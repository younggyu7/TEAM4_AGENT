# Agent 평가

## 문서분석 Agent (`document_analyst`)

평가 기준은 **원문을 빠짐없이 구조화하고, 요구사항을 적절히 묶어 전달하며, 근거를 정확히 검증하는가**다.
LLM이 요구사항을 해석한 결과가 맞는지는 요구사항 Agent 평가에서 따로 본다.

```powershell
python -m evals.eval_document_analyst                                    # 고객요구사항3·5 채점. 결과는 output/eval/<시각>.json·.md
python -m evals.eval_document_analyst --docs 1,2                         # 문서 번호로 고르기 (예: 1 · 1,3 · all)
python -m evals.eval_document_analyst --label after --compare output/eval/<이전>.json   # 변경 전후 비교 (새로 맞힘/새로 틀림)
python -m evals.eval_document_analyst --memory                           # 최대 메모리도 잰다 (tracemalloc 때문에 느림)
```

LLM을 호출하지 않는다. 규칙을 하나 바꿀 때마다 전체 골든셋을 다시 돌려서, 전에 맞히던 사례가 여전히 맞는지도 확인한다.

`doc3/`·`doc5/`의 document_analyst 정답은 처음 받은 골든셋(`golden_tuning_v0.1.json`, 문서 3·5를 한 파일에 묶은 것)을 그대로 나눈 것이다. 받은 원본 파일은 문서별 파일로 대체해 지웠다.

- **검수 전 초안이다** (`human_review_status: pending`). 담당자가 승인하면 v1.0으로 확정한다.
- 골든셋의 모든 문서(1·2·3·5·6)가 **튜닝용**이다. 이 문서들에 맞춰 고친 결과이므로 일반 성능이라고 주장할 수 없다. 튜닝에 쓰지 않은 문서(예: 고객요구사항4, 7~12)로 만든 평가용 골든셋이 필요하다.
- 새 문서를 더할 때는 `doc<번호>/` 폴더를 만들고 채점기의 `DOC_ORDER`에 번호를 넣는다.
- `doc1/`·`doc2/`의 document_analyst 정답은 AI가 파서와 별도로 원문을 읽어 만들었다 (HWPX는 표 XML, PDF는 쪽 글자). PDF의 중첩 표 3개(MPR-001 점검방법, SER-001 패스워드 규칙, PMR-005 산출물)는 쪽 이미지로 구조를 확인해 직접 적었다.
  원본 RFP(`1-2. 제안요청서 1부.pdf`, `2. 제안요청서_KOBACO 정보시스템 통합유지운영.hwpx`)와 요구사항 표 내용이 같음을 확인했다.
  첫 채점(2026-10-28)에서 네 문서 모두 통과하고 Q09(고객요구사항2 MAR-038의 'MPR-002 참조'처럼 없는 요구사항 번호를 가리키는 문제를 경고하는지)만 실패했다. 지금은 그런 검사가 없다.
- `doc6/`의 document_analyst 정답은 원본 엑셀(`인천공항_요구사항.xlsx`, 상세요구사항 415건)의 셀 글자에서 가져왔다. 정제본 PDF는 그중 앞 73건(SFT-001~073)을 옮긴 것이고, 줄 단위로 같음을 확인했다. 예외 두 건:
  - SFT-063: PDF로 바뀌며 긴 셀이 잘려 세 번째 항목 뒷부분 7줄과 '* 입주자포털…' 문장이 PDF에 없다. 정답은 PDF에 남은 데까지다.
  - SFT-068: 마지막 3줄 위에 다른 표(산출물 목록: 착수계·과업수행계획서 등)가 겹쳐 있다. 글자는 파일에 있으므로 정답에 넣었다.

  첫 채점(2026-10-28)에서 드러난 약점 (튜닝 대상):
  - 겹친 표 밑의 3줄을 읽지 못하고 표 글자와 섞는다 (EXT-S068, C22, R45). 겹침을 알리는 경고도 없다 (Q15).
  - SFT-069의 첫 행(요구사항 분류)이 앞 쪽(14쪽) 맨 아래에 따로 떨어져 있어 분류를 못 읽는다 (EXT-S069).
  - 근거 무결성 검사가 전송 수단('SMS'→'SNS', R51)과 '암호화하여'→'평문으로'(R52) 바뀜을 잡지 못한다. 숫자·조건어·대상 목록 밖의 말이다.
- 인용문 검증 정책은 `strict_quote_integrity_v1`이다. 숫자·버전·부정 표현·대상을 바꾼 인용문은 비슷한 원문을 찾았더라도 확인 완료로 만들면 실패다.

### 채점기가 정답을 실제 결과에 연결하는 방법

- 정답 단위(`unit_key`) ↔ 추출 단위(source): 원문 ID가 같은 source 가운데 **제목이 맞는 것**과 연결한다. ID만으로 연결하지 않는다. HWPX3에는 같은 ID를 쓰는 서로 다른 요구사항이 있다.
- 내용 보존: 정답 원문(`reference_text`)을 항목 기호·줄바꿈 기준으로 조각낸다. 각 조각이 source 본문에 있는지 본다. 비교는 NFC 정규화 후 공백·기호를 지우고 한다.
- 출처: PDF는 쪽 번호로, HWPX는 표 순서로 본다. HWPX는 쪽 정보가 없다.
- research 사례: 사례가 가리키는 요구사항의 첫 블록을 '주장한 블록'으로 삼아 요구사항 1건을 만들고, `document_analyst.run(mode=research)`에 넣는다.
  결과는 `verified`(그 자리에서 확인), `relinked`(다른 블록이나 다른 인용문으로 확인), `unconfirmed`(⚠미확인) 가운데 하나로 판정한다.
- 후속 전달 비용: `requirements_analyst`가 보낼 프롬프트를 같은 방식으로 만들어 글자 수를 센다(배치 크기 3 고정). 토큰 수는 API 없이 셀 수 없어 글자 수로 대신한다.

## 요구사항 Agent (`requirements_analyst`)

평가 기준은 **원문을 빠짐없이, 과장 없이, 설계하고 검수할 수 있는 요구사항으로 바꾸는가**다.
문서분석 결과(추출 단위)를 파일로 고정해 두고 넣기 때문에, 앞 Agent(파서)의 오류와 섞이지 않는다.

```powershell
# LLM을 실제로 호출한다 (유료). 같은 입력을 2번 돌려 일관성도 본다
python -m evals.eval_requirements_analyst run --label after --repeat 2 --model claude-haiku-5-5 --compare output/eval/ra/<이전 폴더>/score.json
# 문서 번호로 고르기 (예: 1 · 1,2 · all). 기본은 고객요구사항3·5
python -m evals.eval_requirements_analyst run --label base --repeat 2 --docs 1,2
# 저장된 실행 결과만 다시 채점한다 (무료). 정답지를 고친 뒤에 쓴다
python -m evals.eval_requirements_analyst score output/eval/ra/<실행 폴더>
```

`score`는 모든 문서의 정답지를 읽고 실행 결과에 있는 문서만 채점한다. 결과는 `output/eval/ra/<시각>-<이름>/`에 `run1.json`(LLM 결과), `score.json`, `score.md`로 저장된다.

### 정답지와 입력

문서별 폴더(`golden/doc<번호>/`)의 `ra_inputs.json`(고정 입력)과 `requirements_analyst.yaml`(정답지)을 쓴다.
정답지에는 핵심 진술(필수어·기능/비기능·시스템/업체 의무·분류·우선순위), 꼭 필요한 질문, blocking 허용 주제, 불필요한 질문이 있다.

| 문서 | 정답지 만든 방법 |
| --- | --- |
| `doc3/`·`doc5/` | 진술을 원문을 읽고 직접 작성 (447개, v0.3) |
| `doc6/` | **반자동 초안** (377개, doc1·doc2와 같은 규칙): 구축할 시스템의 기능 목록이라 기본 분류는 기능/시스템/기능이고, 문장 낱말로 다른 해석도 인정 (연계→인터페이스, 암호화·권한→보안, 엑셀·출력→데이터, '공사와 협의'→수행업체 의무) |
| `doc1/`·`doc2/` | **반자동 초안** (907개): 진술은 같은 폴더 document_analyst 정답의 원문을 항목 기호 단위로 나눈 것, 필수어는 프로그램이 고른 숫자(단위 포함)와 드문 명사, 분류·질문은 요구사항별로 직접 정함. 두 문서 모두 유지관리 사업이라 대부분 수행업체 의무(PROJECT)다 |

- **AI가 쓴 검수 전 초안이다.** 고친 이력과 이유는 파일의 `meta.revisions`에 있다.
- 정답은 '요구사항 문장'이 아니라 '핵심 진술'이다. 분해 개수나 표현이 달라도, 진술의 필수어가 한 요구사항(제목+설명+검수 기준)에 모두 있으면 다룬 것으로 본다.
- 우선순위 규칙(`priority_policy`): 원문 응락 수준을 따르고, 없으면 '필수·권장' 같은 표현만 근거로 삼는다. 근거가 없는데 MUST를 확정하면 감점이다.

### 채점 항목

| 묶음 | 지표 | 방법 |
| --- | --- | --- |
| 추출 | 재현율, 의미 왜곡, 중복, 정답에 없는 요구사항(검토용) | 필수어·금지어 대조 |
| 과장 방지 | 원문에 없는 수치로 CONFIRMED, 근거 없는 MUST | 요구사항의 숫자 ⊆ 원문 숫자, 정답 우선순위 |
| 분류 | type·scope·category·priority 정확도 | 정답 허용 목록 |
| 검수 기준 | 원문 충실(원문에 없는 수치), 모호('원활·신속'만 있고 수치 없음), 없음 | 자동 대용 지표. 실제 검증 가능성은 사람이 본다 |
| 근거 | 인용문 원문 일치, 해당 단위 블록인지, 뒷받침(요구사항 수치가 인용문에 있음) | 자동 |
| 질문 | 필요한 질문 포착, 과다 blocking, 불필요 후보 | 정답 주제의 필수어 |
| 안정성·비용 | 결과 없는 단위, 실패 배치, 호출(재시도 포함), 토큰, 시간, 반복 실행 일관성 | 자동 |

### 결과 (claude-haiku-5-5, 각 2회 평균, 정답지 v0.3으로 재채점)

저장된 실행 결과를 정답지 v0.3(원본 RFP 대조 후 보강, 핵심 진술 447개)으로 다시 채점한 값이다.
v0.2로 채점했을 때(진술 410개)는 변경 전 재현율이 98.9%로 나왔는데, 정답지를 촘촘하게 하자 가려졌던 누락이 드러났다.

바꾼 것

1. **우선순위 규칙** ([requirements_analyst.py](../app/agents/roles/requirements_analyst.py) `_priority`, [schemas/requirement.py](../app/schemas/requirement.py)).
   원문 표에 응락 수준이 있으면 코드가 그 값으로 확정한다. 없으면 인용문에 '필수·반드시·권장·선택' 같은 표현이 있을 때만 LLM 값을 인정하고,
   아니면 `UNSPECIFIED`(산출물에는 '미정(원문에 없음)')로 둔다. 전 지시문은 "정보가 없으면 MUST"였다.
2. **지시문**: 여러 항목을 묶어도 항목·숫자·인원·기간·조건을 빠뜨리지 말 것. blocking은 범위 포함 여부·요구 충돌일 때만.
3. **추출 단위 연결**: LLM이 배치에 없는 단위 키를 쓰면, 배치 첫 단위가 아니라 근거 블록이 속한 단위에 연결한다.
4. **fix 모드 질문**: 다시 추출하는 단위의 대기 중 질문은 새 질문으로 바꾼다 (같은 질문이 두 번 쌓이던 문제).

남은 일

- 분류 일관성은 high에서 94.9% → 91.9%로 내려갔다가 medium에서 94.1%였다. 2회 실행씩이라 우연과 구분하기 어렵다.
- effort medium은 품질이 거의 같고 출력 토큰 -45%, 시간 -43%다. `.env`를 medium으로 바꾸면 다른 Agent(기능 명세·데이터 모델·의미 검토)에도 적용되는데, 그쪽은 아직 평가 도구가 없다.
- medium 1회차에서 놓친 진술 5건: 개발언어(안드로이드·Java), 기타정보 선택 항목, validation 노출 확인, 직무 기준 참조, 서버 자원 제안사 제공.
- '권장'처럼 우선순위를 정하는 표현을 모델이 요구사항과 인용문에서 빠뜨리는 경우가 있다 (고객요구사항5 MHR-001). 지금은 '미정'으로 남는다.
- 과다 blocking 판정은 정답지의 허용 주제에 기대므로, 남은 4~5건(대부분 "구축 범위에 들어가는가")이 정말 과다인지 검수가 필요하다.
- 필요한 질문 포착 2/3: 고객요구사항5 DAR-002(정의는 엑셀·PDF, 세부내용은 엑셀만)는 두 번 다 묻지 않았다.
- 정답지 검수(v1.0)와, 튜닝에 쓰지 않은 문서로 만든 평가용 정답지.

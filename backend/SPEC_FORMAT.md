# 개발 스펙 문서 형식 (spec-format v1)

'ERD 최종 확정'으로 만든 최종본(v<ERD>.1 …)에 생기는 개발 스펙 문서 9개의 형식이다 (API 설계 Agent는 최종 확정 때만 돈다).
개발 AI(Claude Code 등)가 이 문서를 읽고 개발할 수 있게, **형식은 코드가 정하고 내용만 산출물에서 채운다**
([app/agents/tools/dev_spec.py](app/agents/tools/dev_spec.py)). 같은 입력이면 항상 같은 문서가 나온다.

- 형식 이름: `spec-format v1`. 모든 문서 머리에 적힌다 (`design.json`의 `meta.dev_spec.format`).
- 형식을 바꿀 때는 `dev_spec.py`와 이 문서를 함께 고치고 번호를 올린다 (v2 …). `tests/test_dev_spec.py`가 두 쪽의 절 제목이 같은지 확인한다.
- 화면에서는 '산출물 보기 → 개발 스펙'의 '형식 보기'로 이 문서를 본다 (`GET /api/v1/spec-format`).

## 공통 규칙

| 항목 | 규칙 |
| --- | --- |
| 머리 | `# 제목` 다음 줄에 `> 프로젝트 · 설계 버전 · spec-format v1`, 그다음 줄에 문서의 목적과 "읽는 순서와 작업 규칙은 AGENTS.md" |
| 절 | 번호가 붙은 `##` 절이 정해진 순서로 나온다. 내용이 없어도 절은 빠지지 않는다 |
| 빈 표 | 행이 없으면 첫 칸에 `없음` 한 줄 |
| 이름 | 테이블·컬럼은 `schema.sql`과 같은 이름 (설계 표준을 쓰면 표준 이름, PostgreSQL DDL은 소문자). 설계 이름 ↔ 표준 이름은 `standard_names.csv` |
| 생성 시각 | 넣지 않는다 (같은 입력이면 같은 문서). 생성 시각은 `design.json`의 `meta.generated_at` |

### ID (코드가 붙인다)

| ID | 뜻 | 만드는 규칙 |
| --- | --- | --- |
| 요구사항 ID | 요구사항 (원문 번호 기반) | 요구사항 Agent |
| `FN-…` | 기능 | 기능 명세 Agent |
| `AC-<기능 ID>-<n>` | 기능 수용 기준 | 기능마다 1부터: 정상 흐름 → 예외 흐름 → 업무 규칙 → 근거 요구사항의 수용 기준 순서 |

| `TASK-001` … | 작업 | 뼈대 001 · DB 002 · 인증 003 · (공통 규칙이 있으면) 공통 004, 그 뒤 기능마다 하나 |

| `Q-`·`RC-`·`CF-`·`FQ-`·`DQ-`·`TQ-` | 고객 확인 질문 | 요구사항·요구사항 검토·충돌·기능 명세·데이터 설계·개발 스펙(기술 스택) |

| 표시 | 뜻 | 수용 기준의 종류 | 개발 AI가 할 일 |
| --- | --- | --- | --- |
| 없음 · `(결정 …)` | 확정 | 규칙 | 그대로 구현 |

## API.md + openapi.yaml — 기능별 API

`API.md`는 사람이 읽는 형식, `openapi.yaml`은 같은 내용의 OpenAPI 3.1 (기준은 `openapi.yaml`).

| 절 | 내용 |
| --- | --- |
| 1. 공통 규칙 | 기본 경로 `/api/v1`, JSON, Bearer 인증, 목록 조회(`page`·`size`, 응답 `{items, page, size, total}`), 오류 응답 `{code, message}`와 공통 오류 400·401·403·500 |
| 2. API 목록 | 표: 메서드 · 경로 · operationId · 기능 · 권한 |
| 3. 기능별 API | 기능마다 `### <기능 ID> <기능명>`, API마다 `#### <메서드> <경로> — <요약> (operationId)`: 권한·경로 변수·목록 여부, 요청 표(필드 · 타입 · 필수 · DB 컬럼 · 설명), 응답 표(필드 · 타입 · DB 컬럼 · 설명), 오류 표(상태 · 코드 · 조건) |
| 4. API가 없는 기능 (배치·자동 실행·내부 처리) | 표: 기능 · 기능명 · 이유 |

필드 타입은 연결한 컬럼에서 코드가 정한다: `bigint` → integer(int64), `integer` → integer(int32), `decimal` → number,
`varchar(n)` → string(maxLength n), `text` → string, `boolean` → boolean, `date` → string(date), `timestamp` → string(date-time),
`jsonb` → object, `uuid` → string(uuid). 허용값이 있으면 `enum`.

`openapi.yaml` 구조: `openapi: 3.1.0` · `info`(사업명, 버전 `v<N>`, spec-format) · `servers: /api/v1` · `security: bearerAuth` ·
`paths`(API마다 `operationId`·`summary`·`tags`(기능 그룹)·`x-function-id`·`x-requirement-ids`·`x-actors`, 경로·쿼리 변수,
요청 본문, 응답 200(DELETE에 응답이 없으면 204), 오류 응답) · `components`(`securitySchemes`, `Error`). 필드마다 `x-db-column`.

메서드·경로는 API마다 하나다. 여러 기능이 같은 메서드·경로를 내면 API 설계가 코드로 정리한다: 다루는 테이블이 다르면
다른 자원이라 경로를 그 테이블 이름의 복수형으로 나누고, 같은 테이블이면 한 API로 두어 앞 기능의 API에
`x-shared-function-ids`(함께 쓰는 기능)를 적는다. 함께 쓰는 기능의 `API.md` 절과 `TASKS.md`에는 그 API를 함께 쓴다고만 적는다.

## ACCEPTANCE_CRITERIA.md — 수용 기준

| 절 | 내용 | 표의 칸 |
| --- | --- | --- |
| 1. 테스트 방침 | 완료 = AC 테스트 통과, 종류별 테스트 방법, '(가정)'·'(보류)' 규칙 처리, 시험 관련 요구사항 | - |
| 2. 기능별 수용 기준 | 기능마다 `### <기능 ID> <기능명>`과 근거 요구사항 | AC ID · 종류(정상·예외·규칙·규칙 (가정)·규칙 (공통)·규칙 (보류 …)·검수) · 조건 (Given) · 동작 (When) · 결과 (Then) · 근거 |
| 3. 비기능 수용 기준 | 시스템 비기능 요구사항 | AC ID · 요구사항 · 분류 · 기준 · 확인 방법 |

종류별로 칸을 채우는 방법: 정상 = 사전 조건 / 정상 흐름 / 출력, 예외 = 사전 조건 / 예외 조건 / 처리,
규칙 = - / 기능 수행 / 규칙 문장(표시는 뗌), 검수 = - / - / 요구사항 수용 기준.

## TASKS.md — 작업 목록

| 절 | 내용 |
| --- | --- |
| 1. 진행 규칙 | 1차(MVP) = 근거 요구사항에 필수(또는 우선순위 미정)가 있는 기능, 2차 = 나머지. 선행 작업, '일부 보류' 처리 |
| 2. 작업 목록 | 표: 작업 · 이름 · 단계 · 선행 작업 · 상태(진행 가능 / 일부 보류 (질문 ID 답 대기)) |
| 3. 작업 상세 | 작업마다 `### TASK-… · <이름> (<단계>)`: 근거 · 선행 작업 · 만들 것(API·테이블) · 완료 기준(AC ID 범위) · 상태 |

작업 순서: 뼈대 → DB 생성 → 인증·권한 → 공통 규칙·코드값(있을 때) → 기능별 (1차 먼저, 같은 단계에서는 외래키상 부모 테이블을 쓰는 기능 먼저,
그다음 기능 그룹 순서·기능 ID 순). 기능 작업의 선행 작업은 DB·인증(+공통 규칙을 쓰면 공통)과, 부모 테이블을 처음 쓰는 작업.
인증·권한 작업의 역할은 기능 명세 공통 결정의 사용자 역할(없으면 사람 행위자)이다. '시스템(…)'·'외부 시스템(…)'은 역할이 아니라
자동 실행·연계 주체로 따로 적는다. API의 권한도 사용자 역할 이름이다.

본 문서는 우리 에이전트가 충족해야 할 요구사항을 정의한다. 고객 문서에서 생성할 ITSM 요구사항 정의서와는 다르다. 아래 요구사항은 별도 표시가 없는 한 **목표 제품 MVP**의 필수 조건이다. 실제 구현 상태와 실행 방법은 [프로젝트 README](../../README.md)와 [TRD](TRD.md)에서 확인한다.

## 2. 용어와 식별자

| 용어·접두어 | 의미 |
| --- | --- |
| FR / NFR / BR | 우리 제품의 기능 / 비기능 / 공통 업무 규칙 |
| AG | 우리 제품의 기능 ID |
| C-REQ / C-FUN / C-TBL / C-COL | 고객 입력으로 생성되는 요구사항 / 기능 / 테이블 / 컬럼 ID |
| 문서 리비전 | 원문 파일과 추출 텍스트를 보존한 입력 버전 |
| 실행 | 특정 문서·답변·모델·설정으로 수행한 분석과 설계 작업 |
| 근거 | 원문 문서·위치·인용문 또는 사용자 답변의 참조 |
| 검토 필요 | 기술 처리 완료 후 사람이 판단해야 하는 사항이 남은 상태 |
| 검증 실패 | 구조 또는 DDL 검증에서 오류가 확인된 완료 상태 |

고객 산출물 ID는 실행 내에서 유일하며 참조 시 실행 ID를 함께 사용한다. 다른 실행에서 같은 ID가 같은 의미를 갖는다고 가정하지 않는다.

## 4. 비기능 요구사항

수치가 포함된 처리 제한은 초기 설계값으로 부하 측정 후 팀이 확정한다. 생성 품질 목표는 가상 평가 세트에서의 목표이며 운영 보장 수치가 아니다.

| ID | 요구사항 | 수용 기준·검증 방법 |
| --- | --- | --- |
| NFR-001 | 산출물 구조 일관성을 유지해야 한다. | 스키마·ID·참조·타입 검증에 실패한 모델의 ERD·SQL 제공이 차단된다. |
| NFR-002 | 요구사항·설계 품질을 측정해야 한다. | 추출 정밀도·재현율, 기능 반영률, 데이터 규칙 충족률 목표 각각 90% 이상으로 평가한다. |
| NFR-003 | 추적·문제 탐지 품질을 측정해야 한다. | 추적 정확도·충족률 목표 각각 90%, 문제 탐지 정밀도·재현율 목표 각각 80% 이상을 기록한다. |
| NFR-004 | SQL과 시각화 일치를 검증해야 한다. | 최종 평가 DDL 실행 성공 목표 100%, ERD·DDL 구조 불일치 목표 0건으로 측정한다. |
| NFR-005 | 입력·실행 비용을 제한해야 한다. | 파일·문자·토큰·시간 상한을 초과하면 명시적 오류를 반환하고 자동 잘라내기를 하지 않는다. |
| NFR-006 | 응답성과 진행 상태를 제공해야 한다. | 로컬 기준 실행 접수 응답 2초 이내를 목표로 하고, 화면은 2초 간격으로 실제 상태를 조회한다. 모델 완료 시간과 분리해 측정한다. |
| NFR-007 | 실패와 재시작에 대응해야 한다. | 단계별 자동 재시도 총 1회 이하, 작업자 중단은 감지 후 실패 상태로 남기며 이전 결과를 보존한다. |
| NFR-008 | 비밀정보와 입력을 보호해야 한다. | 키는 서버 환경 설정에만 두고 브라우저·로그·다운로드에 포함하지 않는다. 업로드 원문은 공개 정적 경로에 두지 않는다. |
| NFR-009 | 문서 내용과 실행 명령을 분리해야 한다. | 문서의 도구 실행·정책 무시 지시로 서버 명령·권한·모델 설정이 변경되지 않는 테스트를 통과한다. |
| NFR-010 | 생성 SQL을 격리해야 한다. | 허용 DDL만 테스트 DB에 적용하고 사용자 제공 연결 문자열과 운영 DB 접근을 허용하지 않는다. |
| NFR-011 | 재현 가능한 실행 기록을 남겨야 한다. | 문서 해시, 모델·프롬프트·스키마·생성기 버전, 단계 시간·사용량·시도 횟수를 저장한다. |
| NFR-012 | 결과를 안전하게 표시·내보내야 한다. | HTML 실행을 방지하고 CSV 수식 시작 문자열을 이스케이프한다. 라벨이 ERD 문법으로 실행되지 않는다. |
| NFR-013 | 부분 저장으로 성공을 오인하지 않아야 한다. | 실행과 산출물의 상태 변경은 트랜잭션으로 처리하고 불완전한 결과는 성공 다운로드에 노출하지 않는다. |
| NFR-014 | 기능·데이터 모델의 변경을 관리해야 한다. | JSON 스키마와 DB 마이그레이션을 버전 관리하고 이전 실행의 스키마 버전을 유지한다. |

## 5. 공통 업무 규칙

| ID | 규칙 |
| --- | --- |
| BR-001 | 실행당 입력 문서 1건을 사용한다. 복수 파일 취합은 MVP에 포함하지 않는다. |
| BR-002 | 분류·설계 결과의 출처는 source, user_answer, proposal로 구분한다. 미해결 여부는 별도 필드로 관리한다. |
| BR-003 | 원문과 사용자 답변이 충돌하면 원문을 삭제하지 않고 사용자 보완으로 바뀐 정책과 근거를 기록한다. |
| BR-004 | 요구사항 없는 설계 요소는 제안 사유가 필요하다. 요구사항처럼 위장하지 않는다. |
| BR-005 | 설계 생성 진행 시 답변 스냅샷을 동결한다. 이후 보완은 새 실행에 반영한다. |
| BR-006 | 구조 오류 또는 DDL 실행 실패가 남으면 completed_with_errors로 표시한다. 기술 실행 불능은 failed로 구분한다. |
| BR-007 | 정보 부족·상충 후보만 남으면 completed_with_warnings로 완료할 수 있다. 결과에 미해결 사항을 포함한다. |
| BR-008 | 구조 오류는 없는 상태에서 DDL 검증이 미실행이면 SQL은 ‘미검증 초안’으로만 제공하며 성공으로 집계하지 않는다. |
| BR-009 | 사람의 확인·오탐 판정은 리뷰 기록이며 스키마·참조·DDL 검증 결과를 덮어쓰지 않는다. |
| BR-010 | 한 프로젝트의 queued·running·awaiting_input 실행은 최대 1개다. 입력 교체 시 대기 실행은 superseded로 종료할 수 있다. |

## 6. 데이터 요구사항

원문 파일·추출 텍스트·근거 위치, 요구사항, 답변, 기능 명세, 데이터 모델, 추적 링크, 검토 결과, 산출물, 실행 메타데이터를 보존한다. 업로드 파일은 불변 리비전으로 저장하며 사용자 답변도 원문과 분리한다.

완료된 실행의 결과 JSON은 불변으로 유지하고, 이후 검토 처분은 별도 기록으로 저장한다. 개인정보를 포함하지 않은 가상 문서만 평가에 사용한다. 보관·삭제 기간은 팀이 데모 운영 전에 확정하며, UI 삭제 기능은 MVP 필수에 포함하지 않는다.

## 7. 검증과 변경 관리

FR은 기능 명세서의 기능별 수용 시나리오로 검증한다. NFR-002~004의 품질 평가는 PRD 목표와 TRD의 고정 평가 절차를 따른다. 나머지 NFR은 오류 주입·경계값·보안·재시작 테스트로 검증한다.

요구사항은 제안 → 합의 → 구현 → 검증 상태로 관리한다. 본 문서의 초기 항목은 모두 제안 상태다. 범위·수치·수용 기준을 변경할 때 관련 AG 기능, TRD, 평가 케이스를 함께 갱신하며 기존 ID를 다른 의미로 재사용하지 않는다.

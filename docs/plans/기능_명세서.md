## 2. 공통 제한과 상태

### 2.1 제한값

변경하면 `.env.example`, 화면 안내와 관련 테스트를 함께 고친다. 괄호는 설정 이름과 기본값이다.

| 항목 | 현재 값·규칙 |
| --- | --- |
| 프로젝트 이름 | 앞뒤 공백 제거 후 1~100자, `/`·`\`·`.`으로 시작 불가. 생략하면 문서 파일 이름 |
| 입력 형식 | PDF·DOCX·HWPX·TXT·MD 한 파일. HWP·DOC·XLSX 등은 변환 방법을 안내하고 막는다 |
| 업로드 크기 | 50MB 이하 (넘으면 413) |
| PDF | 글자 없는 쪽이 절반을 넘으면 스캔본으로 보고 막는다 (OCR 없음) |
| TXT 인코딩 | UTF-8(BOM 포함) → CP949 순으로 읽는다 |
| 단계 재시도 | 기능 명세 `FUNC_FIX_ATTEMPTS`(1) · 데이터 설계 `MODEL_FIX_ATTEMPTS`(1) · DB 검증 `MAX_DB_ATTEMPTS`(1) · 의미 검토 `SEMANTIC_REVIEW_ATTEMPTS`(1) · API 설계 `API_FIX_ATTEMPTS`(1) · 그 밖 `MAX_FIX_ATTEMPTS`(2) |
| 전체 단계 수 | 조정 Agent 판단 `MAX_STEPS`(40)회. 넘으면 지금 초안으로 완료 조건 검사 |
| 동시 LLM 호출 | `LLM_CONCURRENCY`(4) |
| 기능 명세 질문 | '(가정)' 한도 `FUNC_ASSUMPTION_LIMIT`(0.1) · 질문 상한 `FUNC_MAX_QUESTIONS`(12) |
| 동시 작업 | 프로젝트당 진행 중인 작업 1개 (넘으면 409). 서버는 작업자 1개로 띄운다 |

글자 수·토큰·시간 상한은 두지 않는다. LLM 응답이 잘리면 LLM 클라이언트가 다시 요청한다.

### 2.2 작업 상태와 버전 판정

화면 요청(업로드·내보내기·ERD 저장·최종 확정)은 **작업**으로 실행된다.

| 작업 상태 | 화면 표시 | 의미 |
| --- | --- | --- |
| `running` | 진행 중 (경과 초) | CLI 하위 프로세스가 도는 중. 화면은 2초마다 조회한다 |
| `done` | 완료 (경고가 있으면 경고 표시) | 새 버전을 만들었다. 끝나면 새 버전을 연다 |
| `failed` | 실패 | 새 버전 없이 끝났다. 종료 코드별 안내(2: 다시 만들 수 없음, 4: LLM 설정 오류, 5: manual 응답 대기)와 실행 기록 마지막 줄을 보여 준다 |

작업이 확인 질문에서 멈추면(종료 코드 3) 백엔드가 `resume --defer`로 보류 처리하고 이어 간다. 서버를 다시 띄우면 진행 중이던 작업은 실패로 닫는다. 진행 중 취소는 없다.

버전마다 **완료 조건 7개**(요구사항 추출, 원문 근거 연결, 요구사항→기능 추적, 기능→데이터 추적, 데이터 모델 무결성, 차단 질문 해소, 검토 최신화)를 판정해 검토 보고서에 ✅/❌로 적는다. 단계 버전에서 아직 하지 않은 단계의 조건은 '해당 없음'이다.

## 3. AG-00 프로젝트와 실행 시작

**연결 요구사항:** FR-001, FR-020, FR-021.

- 입력: 문서 파일, 프로젝트 이름(선택), 사업 이름(선택, LLM에 사업 맥락으로 줌), DB 검증 여부.
- 출력: 작업(`{job}`), 끝나면 기능 명세 초안 `v1`.
- 흐름: 홈 '새 문서 분석' → `POST /runs` → 형식·크기 검사 → 원본 저장 → `run --defer --until function_designer` 작업 시작 → 문서 분석 → 요구사항 추출·검토 → 기능 명세 → 멈춤.
- 규칙: 같은 프로젝트에 진행 중인 작업이 있으면 시작하지 않는다. 이름이 같은 프로젝트에 다시 올리면 그 프로젝트의 다음 최상위 버전이 된다.
- 예외: 지원하지 않는 형식·스캔 PDF는 400, 크기 초과는 413으로 시작 전에 막는다.
- 수용 시나리오: 업로드가 끝나면 데이터 설계·의미 검토·API 설계를 하지 않은 기능 명세 초안 `v1`이 열린다. 서버를 다시 띄워도 프로젝트와 버전 목록이 보인다.

## 4. AG-01 문서 등록과 텍스트 추출

**연결 요구사항:** FR-002, FR-003.

- 입력: 업로드 원본.
- 출력: 문서 ID·해시, 블록(위치 포함), 추출 단위, 문서 품질 경고.
- 흐름: 형식 판별 → 파싱(요구사항 표 인식·잘린 표 복구·쪽 머리글 제거) → 블록별 위치 → 추출 단위 만들기 → 품질 경고.
- 규칙: 문서 ID·해시는 파일 내용으로 만든다. 표가 없는 본문은 문단 단위로 나눈다. 이 단계는 LLM을 쓰지 않는다.
- 예외: 읽을 수 없는 문서는 작업을 실패로 끝낸다. 일부만 읽힌 경우 품질 경고를 검토 보고서에 남긴다.
- 수용 시나리오: 요구사항의 근거 블록 ID로 원문 위치가 보인다. 스캔 PDF는 분석을 시작하지 않는다. `python -m app parse <문서>`로 LLM 없이 추출 결과를 볼 수 있다.

## 5. AG-02 요구사항 분석

**연결 요구사항:** FR-004, FR-005.

- 입력: 추출 단위와 블록.
- 출력: 요구사항(ID·제목·설명·분류·확정 상태·근거), 확인 질문(Q·RC·CF), 요구사항 검토 결과.
- 흐름: 요구사항 Agent가 추출 단위 묶음마다 추출·분류 → 코드가 인용문을 원문에서 확인 → 요구사항 검토 Agent가 원문 대조(빠진 문장 보충·분류 확인·원문 외 추가 표시)와 충돌 검토.
- 규칙: 원문에 없는 인용문은 다른 블록을 찾아 보고, 없으면 `EVIDENCE_NOT_FOUND`로 남긴다. 상충하는 문장은 합치거나 지우지 않고 충돌 질문(CF)으로 낸다. 분류가 애매하면 분류 질문(RC)으로 낸다.
- 예외: 요구사항이 하나도 없으면 완료 조건 '요구사항 추출'이 미충족이다.
- 수용 시나리오: 요구사항 정의서에 요구사항마다 원문 근거 문장이 붙는다. 원문 외 추가 요구사항은 표시된다.

## 6. AG-03 확인 질문과 답변

**연결 요구사항:** FR-006, FR-007, FR-021, FR-022, FR-023.

- 입력: 기능 명세 화면의 답(선택지 또는 직접 입력), '추천안 맞음' 표시.
- 출력: 답과 확인을 반영한 기능 명세 (내보내기 → ERD 버전, 또는 'AI로 답 반영' → 기능 명세 새 버전).
- 흐름: 기능 명세 화면 '확인 필요'에서 질문·확인 필요 규칙·가정을 본다 → 답하거나 '추천안 맞음'·'가정 맞음'을 표시한다 → 내보내기 때 코드가 반영한다.
- 질문 고르기: 기능 명세 Agent가 설계 뒤 요청 1회로 고른다. 묻지 않으면 '(가정)'이 될 규칙이 한도를 넘는 만큼 질문하고(최대 12개, 같은 결정은 한 질문), 묻지 않은 `(확인 필요)`는 한도 안에서만 추천안 `(가정)`으로 바꾸고 넘으면 `(확인 필요)`로 남긴다.
- 반영 규칙 (LLM 없음): 추천과 같은 답 → 규칙 표시만 `(결정 FQ-…)`. 다른 답 → 그 질문 표시가 붙은 규칙을 답으로 바꾼다. '추천안 맞음' → `(결정)`. 요구사항 질문(RC·CF)의 답은 요구사항 분류·결정에 반영한다.
- 'AI로 답 반영' (선택): 추천과 다른 답이 바꾼 요구사항·기능만 LLM으로 다시 설계해 기능 명세 새 버전을 만든다.
- 예외: 답이 추천과 다르면 화면이 "규칙만 바뀌니 흐름·입력·데이터도 확인하라"고 경고한다. 데이터 설계(DQ)·기술 스택(TQ) 질문은 화면에서 답하지 않고 추천안으로 가정한다.
- 수용 시나리오: 질문에 답하지 않아도 ERD와 최종본이 만들어지고, 남은 질문은 '보류'로 보인다. '추천안 맞음'만 하고 내보내면 그 기능의 테이블은 다시 설계되지 않는다.

## 7. AG-04 기능 명세 생성

**연결 요구사항:** FR-008, FR-022, FR-027.

- 입력: 요구사항, 결정, 질문.
- 출력: 공통 결정(사용자 역할·업무 객체 이름·분류값·공통 규칙·공통 기능)과 기능 명세(ID·이름·설명·행위자·입력·출력·사전 조건·업무 규칙·정상·예외 흐름·데이터·요구사항 연결).
- 흐름: 공통 결정 1회 → 원문 분류(기능 영역)별 그룹을 병렬로 설계 → 행위자를 사용자 역할 이름으로 맞춤 → 확인 질문 고르기 1회 → 요구사항 검토 Agent가 요구사항→기능 연결을 검사 → 기능이 없는 요구사항은 `FUNC_FIX_ATTEMPTS`번 그 요구사항만 채운다.
- 규칙: 공통 규칙은 기능마다 다시 쓰지 않고 `(공통 P…)`로 붙인다. 원문에 없는 판단은 `(가정)`으로 표시한다. 여러 영역이 같은 기능을 요구하면 한 영역에서만 만든다.
- 화면 수정: 기능 명세 화면에서 이름·흐름·규칙 등을 고칠 수 있고, 고친 내용은 내보낼 때 그대로 데이터 설계 입력이 된다.
- 예외: 그룹 요청이 실패하면 그 그룹만 다시 시도하고, 한도를 넘으면 미해결 이슈로 남긴다.
- 수용 시나리오: 같은 사람을 영역마다 다르게 부른 행위자(결재자·승인자)가 역할 이름 하나로 맞춰진다. 기능 명세서 '고객 확인' 절에 '(가정)' 비율과 한도가 보인다.

## 8. AG-05 데이터 모델 생성

**연결 요구사항:** FR-009, FR-021, FR-027.

- 입력: 화면에서 확정한 기능 명세(`--design`), 고친 테이블(`--data-model`), 의견.
- 출력: 테이블·컬럼·PK·FK·허용값·여러 컬럼 제약을 가진 `data_model.json`.
- 흐름: '내보내기 → ERD 만들기' → 엔티티 카탈로그 → 엔티티별 속성 병렬 설계 → 정규화(감사 컬럼 등) → 구조 검사 → 오류가 난 엔티티만 `MODEL_FIX_ATTEMPTS`번 수정 → 추적 검토(코드).
- 규칙: 기준 버전에 데이터 모델이 있으면 이어받아 **바뀐 기능에 연결된 엔티티만** 다시 설계한다(규칙 앞 표시만 바뀐 기능은 바뀐 것으로 보지 않는다). 사람이 고친 테이블은 고정되어 다시 설계하지 않는다. 고친 테이블만 있으면 LLM 없이 정리·검증한다.
- 예외: 남은 구조 오류는 `MODEL_*` 이슈와 완료 조건 '데이터 모델 무결성' ❌로 보인다.
- 수용 시나리오: ERD 화면에서 컬럼을 고치고 저장하면 다음 ERD 번호가 생기고, 그 테이블은 고친 그대로다.

## 9. AG-06 ERD와 DDL 생성 및 검증

**연결 요구사항:** FR-010, FR-011.

- 입력: 데이터 모델.
- 출력: `erd.md`·`erd.mmd`(Mermaid), `schema.sql`(PostgreSQL), 선택 시 `db_validation.md`.
- 흐름: 같은 모델에서 ERD·DDL 생성 → (DB 검증을 켰으면) 검증 DB 임시 스키마에 적용 → 테이블·키·제약 수 확인 → 스키마 삭제.
- 규칙: SQL은 LLM이 쓴 문자열이 아니라 코드 생성기가 만든다. 설계 표준(`--standard`)을 쓰면 ERD·DDL만 표준 이름이다. 검증 DB에 접속할 수 없으면 SQLite로 대체 검증하고 그 사실을 보고서에 적는다.
- 예외: DDL 적용 실패는 데이터 설계 Agent가 `MAX_DB_ATTEMPTS`번 고친다. 다운로드는 막지 않는다.
- 수용 시나리오: FK 대상이 없는 모델은 검증에서 오류로 잡히고 수정 후 다시 검증된다(`test_graph_offline`).

## 10. AG-07 추적표

**연결 요구사항:** FR-012, FR-013.

- 입력: 요구사항·기능·데이터 모델의 연결.
- 출력: `traceability.md`(요구사항 → 기능 → 엔티티, 비기능 → 기능, 엔티티 → 기능, 이전 버전 대비 변경과 영향), `traceability.csv`.
- 규칙: 연결이 있다는 것은 구조적 연결을 뜻하며 내용이 맞다는 뜻이 아니다. 비기능 요구사항은 기능 연결로만 본다. 기능 명세 단계 버전은 엔티티 대신 '데이터 설계 전'과 다시 설계할 엔티티 미리 보기를 보여 준다.
- 예외: 기능이 없는 기능 요구사항(`REQ_WITHOUT_FUNCTION`), 엔티티가 없는 기능(`TRACE_FUNC_WITHOUT_ENTITY`)은 이슈로 남는다.
- 수용 시나리오: 응답 시간 요구사항에 테이블이 없다는 이유로 오류가 생기지 않는다.

## 11. AG-08 누락과 모순 검토

**연결 요구사항:** FR-014, FR-015, FR-024.

- 입력: 요구사항·기능 명세·데이터 모델과 코드 검사 결과.
- 출력: 이슈(종류·심각도·대상 ID·메시지·상태), 최종본의 `semantic_review.md`·`.json`.
- 흐름: 단계마다 코드 검사(모델 무결성·추적 누락) → 'ERD 최종 확정' 때 의미 검토 Agent가 ERD ↔ 기능 명세를 1회 검토(설정으로 기능 명세 ↔ 요구사항 추가).
- 규칙: 의미 검토는 보고만 하고 자동 수정하지 않는다. 근거 인용이 입력에 없거나 대상 ID를 확인할 수 없는 지적, 원문에 없는 세부 요구·앱 처리 지적은 버린다. 화면의 '확인함'·'반영함' 표시는 브라우저에만 남고 검사 결과를 바꾸지 않는다.
- 예외: 의미 검토 요청이 실패하면 최종본 보고서에 '검토 실패(미검증)'로 적는다.
- 수용 시나리오: 업로드·ERD 단계에서는 의미 검토 LLM 호출이 0회이고, 최종 확정 때 1회다(`test_hitl_flow`).

## 12. AG-09 결과 저장과 다운로드

**연결 요구사항:** FR-016~020, FR-026.

- 입력: 프로젝트·버전, 파일 이름.
- 출력: 버전 목록(제목·단계·기준 버전), `design.json`, 산출물 원문, zip, 작업 상태.
- 규칙: 산출물·버전 기록·작업 기록은 서비스 DB에 저장한다. 만든 버전의 산출물은 바꾸지 않고 제목만 바꿀 수 있다. 실제 LLM 실패를 샘플 결과로 바꾸지 않는다. 파일 이름은 허용 목록에 있는 것만 내준다.
- 다운로드: 파일마다 받기, 버전 단위 zip(브라우저에서 묶음). 오류가 남아도 막지 않고 검토 보고서의 완료 조건·이슈로 상태를 알린다.
- 사용량: 검토 보고서의 'LLM 사용량'(호출 수·입력·출력 토큰)을 화면이 보여 준다. 최종본은 최종 확정 단계에서 쓴 양이다.
- 수용 시나리오: 새로고침하거나 서버를 다시 띄워도 같은 버전의 같은 파일을 받는다. 다시 만들어도 이전 버전 파일은 그대로다.

## 13. AG-10 API 설계와 개발 스펙

**연결 요구사항:** FR-025.

- 입력: 확정한 ERD 버전의 기능 명세·데이터 모델·요구사항, 가장 최근 최종본의 API 설계.
- 출력: 최종본의 `api_design`(design.json)과 개발 스펙 9개(`AGENTS.md`·`PRD.md`·`ARCHITECTURE.md`·`DATABASE.md`·`API.md`·`openapi.yaml`·`ACCEPTANCE_CRITERIA.md`·`TASKS.md`·`DECISIONS.md`).
- 흐름: 'ERD 최종 확정' → 추적 검토(코드) → API 설계(기능 `API_BATCH_SIZE`(6)개마다 1회 + 아키텍처 1회, 병렬) → 코드 검사(API 없는 기능·없는 컬럼) → 오류 난 기능만 `API_FIX_ATTEMPTS`번 다시 설계 → 겹친 경로 정리(코드) → 의미 검토 → 개발 스펙 쓰기.
- 규칙: LLM은 경로·권한·필드와 컬럼 연결·오류만 정하고, 필드 타입은 연결한 컬럼에서 코드가 정한다. 기능·연결 테이블의 지문이 같은 기능은 이전 최종본 것을 그대로 쓴다. 문서 형식은 [backend/SPEC_FORMAT.md](../../backend/SPEC_FORMAT.md)(`spec-format v1`)를 따르고 같은 입력이면 같은 문서가 나온다. 원문에 기술 스택이 없으면 `TQ-001`을 추천안으로 가정한다(멈추지 않음).
- 예외: `API_DESIGN=false`면 하지 않고 최종 확정은 추적·의미 검토만 한다. 업로드·ERD 단계에서는 돌지 않는다.
- 수용 시나리오: 같은 ERD를 다시 최종 확정하면 API 설계 LLM 호출이 0회이고 개발 스펙 내용이 같다(`test_dev_spec`).

## 14. 오류 응답과 통합 수용

| 응답 | 경우 | 사용자 안내·복구 |
| --- | --- | --- |
| 400 | 형식이 틀린 값, 지원하지 않는 파일, 허용 목록 밖 파일 이름, 경로 밖을 가리키는 값 | 메시지대로 고쳐 다시 요청 |
| 404 | 없는 프로젝트·버전·파일 | 버전 목록 확인 |
| 409 | 같은 프로젝트에 진행 중인 작업 | 작업이 끝난 뒤 다시 요청 |
| 413 | 50MB 초과 | 파일 줄이기 |
| 작업 실패 (종료 코드 2·4·5) | 다시 만들 수 없음 · LLM 키·크레딧·모델 오류 · manual 응답 대기 | 실행 기록 마지막 줄 확인 후 다시 실행 |

오류 응답 본문은 `{"detail": "..."}`다. 통합 확인은 가짜 LLM으로 업로드 → 내보내기 → ERD → 최종 확정 → 화면 API까지 진행하는 테스트(`test_hitl_flow`·`test_postgres`)로 하며, 실제 LLM 품질은 `backend/evals` 골든셋으로 따로 평가한다.

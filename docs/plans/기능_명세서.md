## 2. 공통 제한과 상태

### 2.1 제한값

변경하면 `.env.example`, 화면 안내와 관련 테스트를 함께 고친다. 괄호는 설정 이름과 기본값이다.

| 항목 | 현재 값·규칙 |
| --- | --- |
| 프로젝트 이름 | 앞뒤 공백 제거 후 1~100자, `/`·`\`·`.`으로 시작 불가. 생략하면 문서 파일 이름 |
| 입력 형식 | 웹 업로드는 PDF·DOCX·HWPX 한 파일(TXT·MD는 CLI만). HWP·DOC·XLSX·이미지 등은 변환 방법을 안내하고 막는다 |
| DOCX·HWPX | 글자가 30자 미만이면 이미지(스캔·캡처)로 된 문서로 보고 업로드에서 막는다 |
| 업로드 크기 | 50MB 이하 (넘으면 413) |
| PDF | 글자 없는 쪽이 절반을 넘으면 스캔본으로 보고 막는다 (OCR 없음) |
| TXT 인코딩 | UTF-8(BOM 포함) → CP949 순으로 읽는다 |
| 단계 재시도 | 기능 명세 `FUNC_FIX_ATTEMPTS`(1) · 데이터 설계 `MODEL_FIX_ATTEMPTS`(1) · DB 검증 `MAX_DB_ATTEMPTS`(1) · 의미 검토 `SEMANTIC_REVIEW_ATTEMPTS`(1) · API 설계 `API_FIX_ATTEMPTS`(1) · 그 밖 `MAX_FIX_ATTEMPTS`(2) |
| 전체 단계 수 | 조정 Agent 판단 `MAX_STEPS`(40)회. 넘으면 지금 초안으로 완료 조건 검사 |
| 동시 LLM 호출 | `LLM_CONCURRENCY`(4) |
| 기능 명세 질문 | 추천안 자동 적용 `AUTO_ASSUME`(true: 꼭 확인할 것만 묻고 나머지는 추천안 '(가정)') · '(가정)' 한도 `FUNC_ASSUMPTION_LIMIT`(0.1, `AUTO_ASSUME=false`일 때) · 고르는 질문만 `ASK_CHOICES_ONLY`(true: 예/아니오 확인·영역 묶음 질문 없이 추천안대로 확정, 기능 명세서 '고객 확인'에 목록) · 질문 상한 `FUNC_MAX_QUESTIONS`(12) |
| 동시 작업 | 프로젝트당 진행 중인 작업 1개 (넘으면 409). 서버는 작업자 1개로 띄운다 |

글자 수·토큰·시간 상한은 두지 않는다. LLM 응답이 잘리면 LLM 클라이언트가 다시 요청한다.

### 2.2 작업 상태와 버전 판정

화면 요청(업로드·내보내기·ERD 저장·최종 확정)은 **작업**으로 실행된다.

| 작업 상태 | 화면 표시 | 의미 |
| --- | --- | --- |
| `running` | 진행 중 (경과 초) | CLI 하위 프로세스가 도는 중. 화면은 2초마다 조회한다 |
| `done` | 완료 (경고가 있으면 경고 표시) | 새 버전을 만들었다. 끝나면 새 버전을 연다 |
| `failed` | 실패 | 새 버전 없이 끝났다. 종료 코드별 안내(2: 다시 만들 수 없음, 4: LLM 설정 오류, 5: manual 응답 대기)와 실행 기록 마지막 줄을 보여 준다 |

작업이 확인 질문에서 멈추면(종료 코드 3) 백엔드가 `resume --defer`로 보류 처리하고 이어 간다. 서버를 다시 띄우면 진행 중이던 작업은 실패로 닫는다. 진행 중 취소는 없다.

버전마다 **완료 조건 7개**(요구사항 추출, 원문 근거 연결, 요구사항→기능 추적, 기능→데이터 추적, 데이터 모델 무결성, 차단 질문 해소, 검토 최신화)를 판정해 검토 보고서에 ✅/❌로 적는다. 단계 버전에서 아직 하지 않은 단계의 조건은 '해당 없음'이다.

## 3. AG-00 프로젝트와 실행 시작

**연결 요구사항:** FR-001, FR-020, FR-021.

- 입력: 문서 파일, 프로젝트 이름(선택), 사업 이름(선택, LLM에 사업 맥락으로 줌), DB 검증 여부.
- 출력: 작업(`{job}`), 끝나면 기능 명세 초안 `v1`.
- 흐름: 홈 '새 문서 분석' → `POST /runs` → 형식·크기 검사 → 원본 저장 → `run --defer --until function_designer` 작업 시작 → 문서 분석 → 요구사항 추출·검토 → 기능 명세 → 멈춤.
- 규칙: 같은 프로젝트에 진행 중인 작업이 있으면 시작하지 않는다. 이름이 같은 프로젝트에 다시 올리면 그 프로젝트의 다음 최상위 버전이 된다.
- 예외: 지원하지 않는 형식·스캔 PDF는 400, 크기 초과는 413으로 시작 전에 막는다.
- 수용 시나리오: 업로드가 끝나면 데이터 설계·의미 검토·API 설계를 하지 않은 기능 명세 초안 `v1`이 열린다. 서버를 다시 띄워도 프로젝트와 버전 목록이 보인다.

## 4. AG-01 문서 등록과 텍스트 추출

**연결 요구사항:** FR-002, FR-003.

- 입력: 업로드 원본.
- 출력: 문서 ID·해시, 블록(위치 포함), 추출 단위, 문서 품질 경고.
- 흐름: 형식 판별 → 파싱(요구사항 표 인식·잘린 표 복구·쪽 머리글 제거) → 블록별 위치 → 추출 단위 만들기 → 품질 경고.
- 규칙: 문서 ID·해시는 파일 내용으로 만든다. 표가 없는 본문은 문단 단위로 나눈다. 이 단계는 LLM을 쓰지 않는다.
- 예외: 읽을 수 없는 문서는 작업을 실패로 끝낸다. 일부만 읽힌 경우 품질 경고를 검토 보고서에 남긴다.
- 수용 시나리오: 요구사항의 근거 블록 ID로 원문 위치가 보인다. 스캔 PDF는 분석을 시작하지 않는다. `python -m app parse <문서>`로 LLM 없이 추출 결과를 볼 수 있다.

## 5. AG-02 요구사항 분석

**연결 요구사항:** FR-004, FR-005.

- 입력: 추출 단위와 블록.
- 출력: 요구사항(ID·제목·설명·분류·확정 상태·근거), 확인 질문(Q·RC·CF), 요구사항 검토 결과.
- 흐름: 요구사항 Agent가 추출 단위 묶음마다 추출·분류 → 빠진 항목 채우기(코드가 원문 목록 항목 중 요구사항에 담기지 않은 것을 찾아 그 단위만 짚어 한 번 더 추출, `REQ_FILL_GAPS`) → 코드가 인용문을 원문에서 확인 → 요구사항 검토 Agent가 원문 대조(빠진 문장 보충·분류 확인·원문 외 추가 표시)와 충돌 검토.
- 규칙: 원문에 없는 인용문은 다른 블록을 찾아 보고, 없으면 `EVIDENCE_NOT_FOUND`로 남긴다. 상충하는 문장은 합치거나 지우지 않고 충돌 질문(CF)으로 낸다. 분류가 애매하면 분류 질문(RC)으로 낸다.
- 예외: 요구사항이 하나도 없으면 완료 조건 '요구사항 추출'이 미충족이다.
- 수용 시나리오: 요구사항 정의서에 요구사항마다 원문 근거 문장이 붙는다. 원문 외 추가 요구사항은 표시된다.

## 6. AG-03 확인 질문과 답변

**연결 요구사항:** FR-006, FR-007, FR-021, FR-022, FR-023.

- 입력: 기능 명세 화면의 답(선택지 또는 직접 입력), '추천안 맞음' 표시.
- 출력: 답과 확인을 반영한 기능 명세 (내보내기 → ERD 버전, 또는 'AI로 답 반영' → 기능 명세 새 버전).
- 흐름: 기능 명세 화면 '확인 필요'에서 질문·확인 필요 규칙·가정을 본다 → 답하거나 '추천안 맞음'·'가정 맞음'을 표시한다 → 필수 항목을 다 해결하면 오른쪽 위 '내보내기 → ERD 만들기'가 초록색으로 켜진다 → 누르면 기능 명세가 확정되고 코드가 답을 반영해 ERD를 만든다.
- 보기 탭: '초안 편집'(기능을 펼치면 맨 위에 그 기능의 남은 확인 항목을 모두 보여 주고 질문 답·체크를 바로 한다. 이미 사람이 체크·답한 항목(필수 포함)과 기능 수정 내용도 누가 했는지와 함께 그 아래에 보이며, 체크를 풀면 다시 남은 항목이 된다. 목록 배지 '확인 n'·'확인함 n'에 마우스를 올리면 종류별 건수) · '확인 필요' · '전체 보기'(묶음별로 기능 이름만 작은 칸으로, 사람이 고친 기능은 파란 테두리와 고친 사람, 남은 확인 항목 수, 사람이 체크하거나 답한 항목 수(초록) 표시. 마우스를 올리면 설명·행위자·규칙 수·고친 칸·남은 확인 항목·확인한 항목(무엇을·누가, 질문은 답까지), 누르면 초안 편집에서 그 기능을 연다) (검토 중)
- 화면 버튼 (내보내기 전후 같음): '기능 명세서 초안' 제목 줄 오른쪽 끝 '임시저장'(서버에 저장, 확정·새 버전 아님 — 누르면 탭 줄 오른쪽 끝에 지난 저장 뒤 바뀐 기능·질문 답·확인 처리 건수를 보여 줌, ERD 화면 '저장하기'와 같음). 오른쪽 위: '원본으로 되돌리기'·'답 n건 AI로 반영 → 기능 명세 다시'(새 답이 있을 때, 없으면 '기능 명세 다시 만들기 (새 버전)')·'내보내기 → ERD 만들기'. 이미 내보낸 기능 명세를 고쳐 다시 내보내면(`rerun data_modeler --from <기능 명세> --design`) 고친 명세를 새 기능 명세 버전(다음 최상위 번호 v2, LLM 없음)으로 남기고 그 ERD(v2.1)를 만든다. ERD는 앞 기능 명세의 최신 ERD를 이어받아 바뀐 기능에 연결된 테이블만 다시 설계한다. 'AI로 답 반영'·'기능 명세 다시 만들기'도 다음 최상위 번호를 받는다(요구사항 단계 버전에서 처음 만드는 기능 명세만 그 아래 번호). 확정 취소는 없다. '기능 명세 다시 만들기 (새 버전)'(`rerun function_designer`: 사람이 고친 기능은 `--functions`로 넘겨 고친 그대로 고정, 답·'추천안 맞음'은 코드로, 의견·추천과 다른 답만 LLM)은 기능 명세 자체를 새 버전으로 만들 때 쓴다. ERD 화면으로는 위 단계 표시줄로 간다. ERD 작업이 실패해 ERD가 생기지 않았으면 다시 내보낼 수 있다.
- 질문 고르기: 기능 명세 Agent가 설계 뒤 요청 1회로 고른다. 묻지 않으면 '(가정)'이 될 규칙이 한도를 넘는 만큼 질문하고(최대 12개, 같은 결정은 한 질문), 묻지 않은 `(확인 필요)`는 한도 안에서만 추천안 `(가정)`으로 바꾸고 넘으면 `(확인 필요)`로 남긴다.
- 반영 규칙 (LLM 없음): 추천과 같은 답 → 규칙 표시만 `(결정 FQ-…)`. 다른 답 → 그 질문 표시가 붙은 규칙을 답으로 바꾼다. '추천안 맞음' → `(결정)`. 요구사항 질문(RC·CF)의 답은 요구사항 분류·결정에 반영한다.
- 'AI로 답 반영' (선택): 추천과 다른 답이 바꾼 요구사항·기능만 LLM으로 다시 설계해 기능 명세 새 버전을 만든다.
- 예외: 답이 추천과 다르면 화면이 "규칙만 바뀌니 흐름·입력·데이터도 확인하라"고 경고한다. 데이터 설계(DQ) 질문은 화면에서 답하지 않고 추천안으로 가정한다. 기술 스택(TQ-001)은 요구사항에 언어·프레임워크 이름이 없을 때 초안에서 코드가 낸 필수 질문이며, 답해도 기능 명세 규칙·ERD는 바뀌지 않는다.
- 수용 시나리오: 질문에 답하지 않아도 ERD와 최종본이 만들어지고, 남은 질문은 '보류'로 보인다. '추천안 맞음'만 하고 내보내면 그 기능의 테이블은 다시 설계되지 않는다.

## 7. AG-04 기능 명세 생성

**연결 요구사항:** FR-008, FR-022, FR-027.

- 입력: 요구사항, 결정, 질문.
- 출력: 공통 결정(사용자 역할·업무 객체 이름·분류값·공통 규칙·공통 기능)과 기능 명세(ID·이름·설명·행위자·입력·출력·사전 조건·업무 규칙·정상·예외 흐름·데이터·요구사항 연결).
- 흐름: 공통 결정 1회 → 원문 분류(기능 영역)별 그룹을 병렬로 설계 → 행위자를 사용자 역할 이름으로 맞춤 → 확인 질문 고르기 1회 → 요구사항 검토 Agent가 요구사항→기능 연결을 검사 → 기능이 없는 요구사항은 `FUNC_FIX_ATTEMPTS`번 그 요구사항만 채운다.
- 규칙: 공통 규칙은 기능마다 다시 쓰지 않고 `(공통 P…)`로 붙인다. 원문에 없는 판단은 `(가정)`으로 표시한다. 여러 영역이 같은 기능을 요구하면 한 영역에서만 만든다.
- 화면 수정: 기능 명세 화면에서 이름·흐름·규칙 등을 고칠 수 있고, 고친 내용은 내보낼 때 그대로 데이터 설계 입력이 된다.
- 예외: 그룹 요청이 실패하면 그 그룹만 다시 시도하고, 한도를 넘으면 미해결 이슈로 남긴다.
- 수용 시나리오: 같은 사람을 영역마다 다르게 부른 행위자(결재자·승인자)가 역할 이름 하나로 맞춰진다. 기능 명세서 '고객 확인' 절에 '(가정)' 비율과 한도가 보인다.

## 8. AG-05 데이터 모델 생성

**연결 요구사항:** FR-009, FR-021, FR-024, FR-027, FR-028.

- 입력: 화면에서 확정한 기능 명세(`--design`), 고친 테이블(`--data-model`), 의견.
- 출력: 테이블·컬럼·PK·FK·허용값·여러 컬럼 제약을 가진 `data_model.json`.
- 흐름: '내보내기 → ERD 만들기' → 엔티티 카탈로그 → 엔티티별 속성 병렬 설계 → 정규화(감사 컬럼 등) → 구조 검사 → 오류가 난 엔티티만 `MODEL_FIX_ATTEMPTS`번 수정 → 추적 검토(코드) → 의미 검토(AG-08) → 데이터 지적과 관련된 테이블만 다시 설계(`MODEL_FIX_ATTEMPTS`번) → 추적 검토 → 의미 검토(남은 지적 확인).
- 화면 (ERD '확인 필요'): 구조 검사 오류와 남은 의미 검토 지적이 필수 항목이다. 의미 검토 지적마다 '반영함·문제 아님·미해결로 둠' 중 하나를 고르고 메모를 남길 수 있다. 필수 항목을 다 해결하고 저장하지 않은 테이블 수정이 없으면 오른쪽 위 'ERD 최종 확정하기'가 초록색으로 켜지고, 한 번 더 확인한 뒤 최종본을 만든다(AG-09). 확정 뒤에는 취소가 없고 'ERD 저장하고 새 버전 만들기'와 '최종 산출물 보기'만 있다.
- 규칙: 기준 버전에 데이터 모델이 있으면 이어받아 **바뀐 기능에 연결된 엔티티만** 다시 설계한다(규칙 앞 표시만 바뀐 기능은 바뀐 것으로 보지 않는다). 사람이 고친 테이블은 고정되어 다시 설계하지 않는다. 고친 테이블만 있으면 LLM 없이 정리·검증하고, 의미 검토를 다시 하지 않으며 이전 버전의 지적과 화면에서 고른 처리(`--dispositions`)를 이어받는다.
- 예외: 남은 구조 오류는 `MODEL_*` 이슈와 완료 조건 '데이터 모델 무결성' ❌로 보인다.
- 수용 시나리오: ERD 화면에서 컬럼을 고치고 저장하면 다음 ERD 번호가 생기고, 그 테이블은 고친 그대로다. ERD를 만들 때 의미 검토가 지적한 테이블만 한 번 다시 설계되고 남은 지적은 '확인 필요'에 나온다(`test_hitl_flow`).

## 9. AG-06 ERD와 DDL 생성 및 검증

**연결 요구사항:** FR-010, FR-011.

- 입력: 데이터 모델.
- 출력: `erd.md`·`erd.mmd`(Mermaid), `schema.sql`(PostgreSQL), 선택 시 `db_validation.md`.
- 흐름: 같은 모델에서 ERD·DDL 생성 → (DB 검증을 켰으면) 검증 DB 임시 스키마에 적용 → 테이블·키·제약 수 확인 → 스키마 삭제.
- 규칙: SQL은 LLM이 쓴 문자열이 아니라 코드 생성기가 만든다. 설계 표준(`--standard`)을 쓰면 ERD·DDL만 표준 이름이다. 검증 DB에 접속할 수 없으면 SQLite로 대체 검증하고 그 사실을 보고서에 적는다.
- 예외: DDL 적용 실패는 데이터 설계 Agent가 `MAX_DB_ATTEMPTS`번 고친다. 다운로드는 막지 않는다.
- 수용 시나리오: FK 대상이 없는 모델은 검증에서 오류로 잡히고 수정 후 다시 검증된다(`test_graph_offline`).

## 11. AG-08 누락과 모순 검토

**연결 요구사항:** FR-014, FR-015, FR-024, FR-028.

- 입력: 요구사항·기능 명세·데이터 모델과 코드 검사 결과.
- 출력: 이슈(종류·심각도·대상 ID·메시지·상태·사람이 정한 처리 `resolution`), 검토 보고서의 '의미 검토' 절, 최종본의 `semantic_review.md`·`.json`(지적과 처리).
- 흐름: 단계마다 코드 검사(모델 무결성·추적 누락) → ERD를 만들 때(`SEMANTIC_REVIEW_MODE=erd`) 의미 검토 Agent가 데이터 모델 ↔ 기능 명세를 검토 → 데이터 누락·제약 누락은 조정 Agent가 데이터 모델 Agent에 한 번 넘겨 관련 테이블만 고친다 → 고친 테이블과 그 테이블을 쓰는 기능만 다시 검토(공통 테이블은 지적 대상 기능만, 다른 테이블은 이름만 넣어 입력을 줄임) → 남은 지적은 ERD 화면에서 사람이 처리를 고른다.
- 규칙: 의미 검토 Agent는 직접 고치지 않는다. 근거 인용이 입력에 없거나 대상 ID를 확인할 수 없는 지적, 원문에 없는 세부 요구·앱 처리 지적은 버린다. 기능 명세는 사람이 확정한 것이라 ERD 단계에서 다시 검토하지 않는다. 사람이 고른 처리는 LLM 지적에만 남고 코드 검사 결과를 바꾸지 않는다. 같은 지적이 고친 뒤 다시 나오면 처리는 지워지고 다시 고른다.
- 예외: 의미 검토 요청이 실패하면 보고서에 '검토 실패(미검증)'로 적는다. 'ERD 최종 확정'에서는 의미 검토를 하지 않는다.
- 수용 시나리오: 업로드에서는 의미 검토 호출이 0회이고, ERD를 만들 때 검토 → 고치기 → 다시 검토가 한 번씩 돈다. 사람이 고친 ERD만 저장하거나 최종 확정하면 의미 검토 호출이 0회다(`test_hitl_flow`).

## 12. AG-09 결과 저장과 다운로드

**연결 요구사항:** FR-016~020, FR-026, FR-028~030.

- 입력: 프로젝트·버전, 파일 이름.
- 출력: 버전 목록(제목·단계·기준 버전), `design.json`, 산출물 원문, zip, 작업 상태.
- 규칙: 산출물·버전 기록·작업 기록은 서비스 DB에 저장한다. 만든 버전의 산출물은 바꾸지 않는다. 제목, 최종본의 기술 스택 확정(AG-10)만 예외다. 실제 LLM 실패를 샘플 결과로 바꾸지 않는다. 파일 이름은 허용 목록에 있는 것만 내준다.
- 다운로드: 파일마다 받기, 버전 단위 zip(브라우저에서 묶음). 오류가 남아도 막지 않고 검토 보고서의 완료 조건·이슈로 상태를 알린다.
- 사용량: 검토 보고서의 'LLM 사용량'(호출 수·입력·출력 토큰)을 화면이 보여 준다. 최종본은 최종 확정 단계(API 설계)에서 쓴 양이다.
- 최종 확정 (`review`, 화면 'ERD 최종 확정하기'): 화면에서 고른 지적 처리(`--dispositions`)를 남김 → 모델 오류가 남았으면 멈춤 → 생성 DDL을 검증 DB에 적용, 실패하면 최종본을 만들지 않음 → 추적 검토(코드) → API 설계(AG-10) → 최종본(v<ERD>.1)에 ERD·DDL·산출물·개발 스펙과 `db_validation.md`를 쓴다. 각 단계는 판단 기록에 이어 붙는다(`mode: final`).
- 최종 산출물 화면은 보기만 한다: 최종 ERD·DDL·산출물 파일·개발 스펙 파일, 의미 검토 지적과 처리. 확정·다시 검토 버튼은 없다. 예외로 '개발 스펙 파일'에서 기술 스택을 고를 수 있다(추천 선택지·직접 입력 → '이 스택으로 확정', 확정 뒤 '바꾸기').
- 수용 시나리오: 새로고침하거나 서버를 다시 띄워도 같은 버전의 같은 파일을 받는다. 다시 만들어도 이전 버전 파일은 그대로다.

## 13. AG-10 API 설계와 개발 스펙

**연결 요구사항:** FR-025.

- 입력: 확정한 ERD 버전의 기능 명세·데이터 모델·요구사항, 가장 최근 최종본의 API 설계.
- 출력: 최종본의 `api_design`(design.json)과 개발 스펙 9개(`AGENTS.md`·`PRD.md`·`ARCHITECTURE.md`·`DATABASE.md`·`API.md`·`openapi.yaml`·`ACCEPTANCE_CRITERIA.md`·`TASKS.md`·`DECISIONS.md`).
- 흐름: 'ERD 최종 확정' → DDL 검증·추적 검토(코드) → API 설계(기능 `API_BATCH_SIZE`(6)개마다 1회 + 아키텍처 1회, 병렬) → 코드 검사(API 없는 기능·없는 컬럼) → 오류 난 기능만 `API_FIX_ATTEMPTS`번 다시 설계 → 겹친 경로 정리(코드) → 개발 스펙 쓰기.
- 규칙: LLM은 경로·권한·필드와 컬럼 연결·오류만 정하고, 필드 타입은 연결한 컬럼에서 코드가 정한다. 기능·연결 테이블의 지문이 같은 기능은 이전 최종본 것을 그대로 쓴다. 문서 형식은 [backend/SPEC_FORMAT.md](../../backend/SPEC_FORMAT.md)(`spec-format v1`)를 따르고 같은 입력이면 같은 문서가 나온다. 기술 스택은 기능 명세 화면에서 답한 `TQ-001`을 먼저 넣어 두는 값(가정 — 기능 명세에서 고른 값)으로 쓰고, 답이 없으면 추천안으로 가정한다(멈추지 않음). '확정'은 최종 산출물 화면에서 골랐을 때만이다(버전 기록 `tech_stack`). 아키텍처 요약이 원문에서 스택을 찾으면 원문이 우선이다. 최종 산출물 화면 '개발 스펙 파일'에서 스택을 고르면(`POST /projects/tech-stack`) 코드가 같은 최종본의 개발 스펙 9개를 다시 쓰고 design.json의 TQ-001 답·`meta.dev_spec`, 버전 기록 `tech_stack`에 남긴다(LLM 없음, 설계 산출물은 그대로). 업무 동작 분석 전에 만든 예전 최종본(BEHAVIOR.md 없음)은 같은 카드에 '빠진 파일 채우기'가 보이고, 누르면(`POST /projects/dev-spec/fill`, PM·개발자) 그 최종본으로 업무 동작 설계를 한 번(LLM 1회) 하고 개발 스펙을 다시 쓴다. 확인 질문은 바로 묻지 않고 미룬다(BQ-…, DEFERRED). 실패하면 파일을 그대로 두고 오류를 보인다 (검토 중).
- 예외: `API_DESIGN=false`면 하지 않고 최종 확정은 DDL 검증·추적 검토만 한다. 업로드·ERD 단계에서는 돌지 않는다.
- 수용 시나리오: 같은 ERD를 다시 최종 확정하면 API 설계 LLM 호출이 0회이고 개발 스펙 내용이 같다(`test_dev_spec`).

## 14. 회원·권한·함께 쓰기

**연결 요구사항:** FR-032, FR-033, FR-034, FR-035, FR-036, FR-045, FR-048.

- 입력: 회원가입(이름·이메일·비밀번호·희망 역할), 로그인(이메일·비밀번호·로그인 유지), 관리자의 역할·승인·중지, 수정 초안(버전·상태·rev), 최종 결정(승인 / 수정 지시 + 단계·지시 내용).
- 출력: 로그인 세션 쿠키, `GET /auth/me`의 회원·권한 목록, 서버 초안(`draft-v<버전>.json`), 최종본 버전 기록의 `approval`·`approvals`, 버전마다 `created_by`.
- 흐름: 가입 → (처음 가입자는 관리자·PM으로 바로, 그 뒤는 승인 대기) → 관리자가 회원 관리 화면에서 역할을 정해 승인 → 로그인 → 역할에 맞는 단계를 고치고(초안은 서버에 1.2초마다·확정·임시저장 때 저장, 서버가 변경 내역을 남김) 개발자가 기능 명세 '수정 완료 승인 요청' → PM이 변경 내역을 보고 확정(PM은 요청이 없어도 확정) → PM·개발자가 ERD 최종 확정(승인 요청 없음) → PM·개발자가 최종 승인 또는 수정 지시 → 수정 지시는 그 단계 화면 위에 보이고, 개발자가 새 버전을 만들어 다시 최종 확정한다.
- 규칙: 권한은 서버가 API마다 검사한다(`app/core/auth.py` PERMISSIONS, 403과 누가 할 수 있는지). 화면은 같은 표로 버튼을 끄고, 고칠 권한이 없는 단계의 입력칸을 끈다(보기 전용). 초안 저장은 불러온 rev와 서버 rev가 같을 때만 되고, 다르면 409와 먼저 저장한 사람을 알린다. 최종본에는 초안이 없다(400). 관리자가 한 명도 남지 않게 바꿀 수 없다. 회원을 중지·대기로 바꾸면 그 회원의 세션을 지운다. 회원 테이블은 서비스 DB(Alembic `users`·`user_sessions`), 서비스 DB가 없으면 `OUTPUT_DIR/service.sqlite`다.
- 예외: 로그인하지 않으면 401(화면은 로그인으로), 승인 대기·중지 계정의 로그인은 403, 같은 이메일 가입은 409, 다른 사람이 먼저 저장한 초안은 409.
- 수용 시나리오: 처음 가입자는 PM·관리자, 두 번째는 승인 대기 → 역할을 정해 승인하면 로그인. 개발자는 기능 명세 새 버전은 되지만 내보내기는 403(승인 요청은 됨), ERD 최종 확정은 PM·개발자 모두 요청 없이 되고 ERD 승인 요청은 400, 업로드는 PM·개발자. 개발자가 저장한 초안을 PM이 보고, 늦게 저장하면 409. 수정 지시는 PM·개발자, 단계와 내용이 없으면 400(`test_api`).
- 반려 (제안): 기능 명세 승인 요청 배너에서 PM이 사유(필수, 500자)를 적어 '반려'한다(`POST /drafts/request/reject`). 요청은 닫히고 변경 내역에 '반려'로 남으며, 개발자가 다시 요청하거나 확정될 때까지 화면 위에 반려 사유가 보인다. 개발자는 403, 사유가 비면 400, 열린 요청이 없으면 404.
- 프로젝트 담당자 (검토 중, FR-048): 고른 담당자만 그 프로젝트를 본다. 업로드 화면 '담당자'에서 고른 회원 + 올린 사람이 담당자가 되고(Slack이 꺼져 있어도, `POST /runs`의 `members`), PM도 고른 PM만 보고, 담당자에는 PM이 최소 한 명 있어야 한다(업로드·담당자 바꾸기 때 화면이 버튼을 끄고 서버도 400). PM을 고른 적이 없는 프로젝트(이 규칙 전에 만든 프로젝트·CLI로 만든 프로젝트, 고른 PM이 모두 사용 중지됨)는 PM 모두가 보고 담당자로 친다. PM이 없으면 '올리고 분석 시작'·담당자 '저장'이 꺼지고 마우스를 올리면 'PM 최소 한 명은 필요합니다'가 뜬다. 프로젝트 화면 오른쪽 '담당자' 카드에서 PM만 '바꾸기'로 더하거나 뺀다(`GET·POST /projects/members`, Slack 채널이 있으면 초대·내보내기도). 담당자가 아니면 프로젝트 목록·'나에게 온 알림'에서 빠지고, 그 프로젝트를 받는 API·작업 조회는 404(화면은 '이 프로젝트를 볼 수 없습니다'), Slack 알림도 받지 않는다. 같은 이름으로 업로드하면 409. 서버는 `api/v1/deps.py`의 `_project`·`_file`에서 요청한 회원을 검사한다(`services/project_access.py`, `project_members` 테이블). 수용 시나리오는 `test_project_access`.
- Slack 알림 (제안, 팀 워크스페이스 하나 + 프로젝트별 채널): 봇 토큰은 `.env` `SLACK_BOT_TOKEN` 하나(비우면 끔, 권한 `chat:write`·`groups:write`). 업로드하면 서버가 비공개 채널 `#team4-<프로젝트>`를 만들고(이름이 있으면 `-2`, 한글 이름을 받지 않으면 영문 이름) 그 프로젝트의 담당자를 초대한다. 채널이 없는 프로젝트는 서버가 만들고 담당자를 초대한다. Slack이 실패해도 업로드·분석은 하고 10분 뒤 다시 만든다. 채널 멤버는 담당자 중 실제로 초대된 회원이다(ID가 없거나 워크스페이스에 없으면 초대하지 못하고 이유를 보여 줌, 담당자가 아닌 회원은 초대·멘션하지 않음). 알림은 받는 담당자 중 채널에 있는 회원을 멘션하고, 아무도 채널에 없으면 PM을 대신 멘션하며 빠진 역할·이름을 안내한다(승인·반려 결과도 부를 사람이 채널에 없으면 안내). 중간에 담당자가 바뀌면 프로젝트 화면 '담당자' 카드에서 PM이 다시 고른다(`POST /projects/members`, PM이 아니면 403): 더한 회원은 초대, 뺀 회원은 채널에서 내보내고 채널에 '담당자 변경'을 올린다. 그 채널에 홈 '나에게 온 알림'의 새 항목을 알림마다 메시지 하나로 올리고(그 알림을 받는 담당자를 @멘션, 같은 알림은 한 번만), PM의 기능 명세 확정은 '승인'으로 요청한 개발자를, 반려는 '반려(사유)'로 요청한 개발자와 그 초안을 고친 개발자 담당자를(이들의 홈 '나에게 온 알림'에도 반려가 다시 요청하거나 새 버전이 생길 때까지 남고 Slack에는 다시 안 올림), 최종 승인은 그 최종본·바탕 ERD·기능 명세를 만들거나 고친 회원을, 수정 지시는 그 회원과 지시를 처리할 개발자를 멘션해 올린다(결정한 사람 자신 빼고, 같은 지시의 '수정 지시' 알림은 따로 안 올림). 회원 Slack 멤버 ID는 회원가입(선택)·관리자 페이지에서 넣는다(형식 `U`·`W` + 영문 대문자·숫자, 틀리면 400). Slack 실패는 화면 요청을 막지 않고 서버 로그에만 남는다. 수용 시나리오는 `test_slack`(가짜 Slack API).

## 15. AG-11 최종 개발하기·미리보기·git 올리기 (검토 중)

**연결 요구사항:** FR-038, FR-039, FR-040, FR-041, FR-042.

- 입력: PM이 승인한 최종본(개발 스펙 10개·ERD·DDL·API 설계), PM이 고른 스택(화면·백엔드·DB), 'AI로 업무 로직 채우기' 여부, git 저장소 설정.
- 출력: 서버 코드 폴더 `OUTPUT_DIR/<프로젝트>/app`(frontend·backend·db·spec), 미리보기 빌드 `app/.preview/{mock,server}`, 실행 컨테이너 `reqagent-app-<키>`, 최종본 기록 `develop`·`git`.
- 흐름: 최종 승인 → 개발자 알림 → 개발자 '최종 개발하기'(예상 확인 → `develop` CLI → 예시 데이터 화면 빌드) → 최종 개발물 화면(단계 표시줄 '개발 진행'·'테스트(검증)'·'실행·마무리', 최종 승인 뒤 열림, 개발을 시작하면 1단계로 이동. 1단계 개발(파일 구성·코드 보기, 빈 업무 로직 표시, 브랜치를 골라 개발자가 고쳐 저장하기(커밋) — main은 읽기만, 검토 중)·2단계 실행(터미널: 빌드·실행 출력과 앱 서버 로그)·3단계 Git으로 나눠 보이고, 위의 '결과물 미리보기'는 1단계면 예시 데이터 화면, 2·3단계면 새 탭에서 안내 페이지 → Docker로 백엔드·DB 실행 → 앱 화면, 10분 안 보면 끔) → 브랜치에서 합치기 요청 → 개발자가 차이 보기·합치기 또는 반려(오른쪽 '코드 저장소' 이력 그래프, FR-046, 검토 중) → 3단계 원격 올리기(처음엔 원격 하나 설정 → 코드 저장소의 main과 최종본 태그 push, 원격에 서버에 없는 커밋이 있으면 거부).
- 규칙: 코드 생성은 스펙대로 코드가 하고(LLM 없음), AI는 고른 경우 업무 로직 빈칸만 채운다([docs/DEVELOP.md](../DEVELOP.md)). 생성 앱은 Docker 안에서만 실행한다(서버 PC에 Java·Maven 불필요). 앱 포트는 127.0.0.1의 18080~18199, 동시 3개. 토큰은 암호화 저장·기록에서 가림.
- 예외: 승인 전 최종본 400, 개발 권한 없음 403, 백엔드 틀이 없는 스택이면 화면·DB만 만들고 예시 데이터 미리보기만, Docker·Node가 없으면 그 단계만 실패로 알린다.
- 수용 시나리오: 승인 전에는 예상·개발이 400, 승인 후 개발자만 202(PM은 403), 승인하면 개발자 알림·개발하면 사라짐. 미리보기 파일은 로그인 회원만·폴더 밖 404. 스택은 지원하는 조합만. git은 화면·백엔드 저장소에 정해진 파일만, 토큰은 기록에 없음, 다시 올리면 바뀐 것만(`test_develop_screen`). 이 PC에서 생성 앱을 Docker로 띄워 프록시로 API 200을 확인했다.

## 16. AG-12 개발 분배·검토·VS Code 확장 (검토 중)

**연결 요구사항:** FR-049, FR-050, FR-051, FR-052, FR-053, FR-054.

- 입력: 최종 개발하기로 만든 코드 저장소(gen·dev), 프로젝트 담당자, 개발 스펙(기능별 TASKS·API·BEHAVIOR·완료 기준 절), 개인 접속 토큰(확장).
- 출력: 화면 구성 `frontend/src/generated/layout.json`(format 2: 업무 영역 `sections[{id, name, menus}]`·메뉴·홈 칸), 메뉴 화면 파일 `frontend/src/menus/*.tsx`, 작업 기록(프로젝트 파일 `work.json`), AI 생성 결과 브랜치 `gen`, 작업 브랜치 `task/<묶음>`, 릴리스 태그 `release-<날짜>-<n>`(첫 릴리스 때 `main` 생성), 확장에 내려주는 작업 코드와 `.task/TASK.md`·`files.txt`·`RULES.md`.
- 흐름: 최종 개발하기 → gen 커밋(처음이면 dev도 같은 커밋, 다시 개발이면 gen → dev 합치기 요청을 다른 개발자가 승인) → (선택) 화면 구성 · 업무 영역 조정(규칙·AI 제안 → 사람이 고쳐 저장) → 1단계 '작업 묶음'에서 개발자가 담당자 배정(칸·영역 줄을 골라 한꺼번에 가능, 그때의 dev에서 묶음마다 브랜치 생성, 알림은 한 번) → 담당자가 VS Code 확장에서 코드 받기(최신 dev를 넣어 줌) → 개인 AI·직접 개발 → Docker 실행 확인 → 변경 확인(원본/수정 비교) → 바뀐 파일 올리기·제출(합치기 요청) → 다른 개발자가 비교 화면에서 승인(dev에 합침)·반려(사유) → 개발자가 dev를 원격에 올리면 테스트 배포 → '릴리스'(dev → main + 태그, 첫 릴리스가 main을 만듦) → main 올리기.
- 영역 규칙: 최종 개발하기는 규칙으로 묶는다(메뉴마다 화면의 주 테이블 집합·이름 낱말을 보고, 둘 중 큰 자카드 값이 0.2 이상인 묶음부터 하나씩 합침. 메뉴가 4개 이상이면 메뉴 셋 중 하나 넘게 나오는 테이블·낱말은 뺌. 이름은 둘 이상의 메뉴에 나오는 낱말, 없으면 앞 두 메뉴 이름). 영역 id는 만들 때 첫 메뉴 그룹이고 이름을 바꾸거나 메뉴를 옮겨도 유지한다(AI 제안도 첫 메뉴가 같은 예전 영역의 id를 이어 씀). 저장할 때 모르는·겹친 메뉴는 빼고, 빠진 메뉴는 규칙으로 묶어 끝에 붙이고, 빈 영역은 지운다.
- 묶음 규칙: 공통 화면 틀 `common-ui`(App·Login·Screen·kit·menu·theme·api·main 등 frontend 틀과 화면 구성), 화면 `screen-<영역>`(그 영역 메뉴들의 화면 파일 + 그 기능들의 AI 화면 `pages/<기능>.tsx`), 공통 서버·DB `common-server`(인증·공통 코드·조회 API·schema·seed·Docker·문서, 메뉴가 없는 자동 실행 기능), 서버 `server-<영역>`(그 영역 기능들의 API·업무 로직·인수 테스트). 예전 키(`ui-<메뉴>`·`fn-<기능>`)의 작업 기록은 목록에 보이지 않는다. 파일 이름은 기능 ID에서 정해지므로(`FN-SFR-001-05` → `FnSfr00105`) 이름이 겹치지 않는다. 생성기 관리 파일(`generated/*`, `pages/index.ts`, `menus/index.ts`)은 공통 화면 틀 묶음에만 둔다.
- 규칙: 배정·제출·승인·반려는 개발자(`develop` 권한)만, 제출은 담당자 본인만 한다. 본인 승인 금지, 프로젝트의 개발자 담당자가 1명이면 허용(기록에 '본인 승인'). gen은 최종 개발하기만 커밋하고, gen → dev 요청도 개발하기만 낸다(요청한 사람 = 개발하기를 누른 개발자, 열린 요청은 하나). 반려한 gen 변경은 gen에 남아 다음 재생성 요청에 함께 들어간다. 제출 때 바뀐 파일이 묶음 밖이면 400. 진행 중인 묶음(요청 옴~승인 대기·반려)이 있는 영역은 화면 구성에서 메뉴를 넣거나 빼지 못한다(이름은 가능). 작업 기록은 묶음 키로 보관하므로 다시 개발해 파일이 바뀌어도 배정은 남는다. 확장 토큰은 해시만 저장하고 만든 회원 권한으로만 동작한다. 토큰은 홈 오른쪽 '확장 접속 토큰'(만들기·목록·지우기)과 최종 개발물 오른쪽 '확장 연결'(코드 저장소 아래, `develop` 권한만 보임: 서버 주소 복사·토큰 만들기·목록·지우기·이 프로젝트의 내 작업)에서 다룬다.
- 확장 코드 받기 위치: 지금 연 폴더 아래 `<프로젝트>__<묶음>`에 받고 새 창은 열지 않는다(연 폴더의 다른 파일은 그대로). 폴더를 안 연 창이면 기본 폴더(`~/team4-work`)를 그 창에서 연다. 다른 곳에 받아 올리지 않은 변경이 있으면 그 폴더를 현재 창에 더하고, 연 폴더가 다른 작업 폴더 자체면 겹쳐 받지 않고 기본 폴더에 받아 더한다. 같은 이름의 폴더에 다른 파일이 있으면 받지 않는다. 사이드바의 받은 작업 아래에는 `TASK.md`·`files.txt`, 이어서 `files.txt`의 파일만 담은 폴더 나무(폴더는 접힘, 파일만 없는 폴더는 한 줄로 줄임, 바뀐 파일은 표시하고 누르면 비교)가 있고(전체 코드는 탐색기), 목록 밖 변경은 `목록 밖 변경 N개` 한 줄로 알리며 누르면 변경 확인이 열리고, `RULES.md`는 요청 옴(없으면 첫 작업 상태) 맨 위에 한 줄이다. 작업 줄을 더블클릭하면(같은 줄을 0.5초 안에 다시 누름) 작업 패널이 열리고, 연 폴더의 `search.exclude`에 다른 작업 폴더를 넣어 검색·빠른 열기를 그 작업으로 좁힌다(사람이 넣은 항목은 유지). `TASK.md`는 코드를 받을 때 옆에 열리고(다른 작업의 것은 닫음) 그 밖에는 사이드바에서 누를 때만 열린다. 승인 대기·완료 묶음은 비어도 0으로 항상 보인다. 코드를 받기 전 작업도 펼치면 `files.txt`와 같은 파일 나무가 보인다(누르면 열리는 것은 받은 뒤). 완료 작업은 `TASK.md`·`files.txt` 없이 합치기 커밋에서 바뀐 파일(`GET /develop/work/mine`의 `changed_files`)만 나무로 보이고, 기록이 없으면 한 줄로 알린다.
- 예외: 담당자가 아닌 회원 배정 400, 이미 진행 중인 묶음 다시 배정 409(반려·완료 뒤에는 가능), 커밋 안 한 변경·앞선 커밋 없음 400, 충돌이면 409와 충돌 파일(gen 요청이면 'AI가 바꾼 파일을 사람도 고침' 안내), gen·dev·main 직접 수정·요청 400, 첫 릴리스 전 main 올리기 400, 틀린 토큰 401, 진행 중인 영역의 메뉴 이동 400, AI 영역 제안 실패 502(규칙 결과로 바꾸지 않음), 일괄 배정은 묶음별 결과(일부 실패해도 나머지 배정). 코드 받기에서 최신 dev와 충돌하면 받기는 되고 충돌 파일을 알린다.
- 수용 시나리오: 묶음 4종(공통 2 + 영역마다 화면·서버)이 보이고 파일이 빠짐없이 한 묶음에 들어간다. 비슷한 메뉴(같은 테이블·이름 낱말)는 한 영역이고 모두가 쓰는 테이블로는 이어지지 않는다. 영역이 없는 예전 화면 구성도 영역으로 읽힌다. 영역 줄을 골라 한 번에 배정하면 화면·서버 묶음이 함께 배정되고 알림은 하나다. 진행 중인 영역의 메뉴를 옮기면 400이다. AI 제안은 저장하지 않고, 실패하면 502다. 배정 → 브랜치 생성 → 커밋 → 제출 → 다른 개발자 승인 → dev에 합쳐지고 상태 완료, 같은 사람 승인은 403(개발자 1명이면 허용). 토큰으로 내 작업 목록·코드 받기·올리기·제출이 된다. 첫 결과물 홈에 업무 카드 나열이 없고 같은 테이블 화면이 한 화면이다. 처음 개발 뒤 gen = dev이고 main이 없다. 다시 개발하면 dev는 그대로이고 gen 요청을 승인해야 바뀐다. 다른 사람이 dev에 합친 뒤 코드를 받으면 그 내용이 들어 있다. 첫 릴리스가 main을 만든다.

## 17. 오류 응답과 통합 수용

| 응답 | 경우 | 사용자 안내·복구 |
| --- | --- | --- |
| 400 | 형식이 틀린 값, 지원하지 않는 파일, 허용 목록 밖 파일 이름, 경로 밖을 가리키는 값 | 메시지대로 고쳐 다시 요청 |
| 401 | 로그인하지 않음·세션이 끝남 | 로그인 화면으로 |
| 403 | 이 단계를 할 역할이 아님, 승인 대기·중지 계정 | 메시지의 담당 역할에게 요청, 관리자 승인 |
| 404 | 없는 프로젝트·버전·파일 | 버전 목록 확인 |
| 409 | 같은 프로젝트에 진행 중인 작업, 같은 이메일 가입, 다른 사람이 먼저 저장한 초안 | 작업이 끝난 뒤 다시 요청 · '다시 불러오기' |
| 413 | 50MB 초과 | 파일 줄이기 |
| 작업 실패 (종료 코드 2·4·5) | 다시 만들 수 없음(최종 확정은 모델 오류·DDL 검증 실패 포함) · LLM 키·크레딧·모델 오류 · manual 응답 대기 | 실행 기록 마지막 줄 확인 후 다시 실행 (최종 확정이 실패하면 ERD를 고쳐 새 버전에서 다시 확정) |

오류 응답 본문은 `{"detail": "..."}`다. 통합 확인은 가짜 LLM으로 업로드 → 내보내기 → ERD → 최종 확정 → 화면 API까지 진행하는 테스트(`test_hitl_flow`·`test_postgres`)로 하며, 실제 LLM 품질은 `backend/evals` 골든셋으로 따로 평가한다.

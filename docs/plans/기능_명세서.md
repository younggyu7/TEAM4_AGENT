## 2. 공통 제한과 상태

### 2.1 초기 제한값

아래 값은 구현·평가를 위한 제안 기본값이다. 변경 시 서버 설정, 화면 안내와 관련 테스트를 함께 갱신한다.

| 항목 | 기본값·규칙 |
| --- | --- |
| 프로젝트 이름 | 공백 제거 후 1~100자 |
| 프로젝트 설명 | 2,000자 이하 |
| 입력 | 실행당 PDF·DOCX·UTF-8 TXT 중 한 파일, 10 MiB 이하 |
| PDF | 50페이지 이하, 텍스트 추출 가능 문서 |
| 추출 본문 | 공백 제외 최소 1자, 정규화 후 30,000자 이하 |
| DOCX 내부 확장 크기 | 총 50 MiB 이하; 외부 리소스 가져오기 금지 |
| 질문 답변 | 질문당 2,000자, 합계 10,000자 이하 |
| 모델 입력 | 본문·답변·선행 결과 합산 토큰 예산 검증; 초과 시 실패, 자동 절삭 금지 |
| 단계 시간 | 외부 호출을 포함한 단일 시도 120초, 실행 전체 활성 처리 15분 이하 |
| 자동 재시도 | 단계별 최초 시도 외 최대 1회; 형식 복구·일시 오류를 합산 |
| 동시 실행 | 프로젝트당 활성 실행 1개, 로컬 작업자 동시 처리 1개 |

시간과 크기는 모델·환경 측정 후 확정한다. 질문 응답 대기와 작업 대기열 시간은 활성 처리 제한에서 제외한다. 문서가 상한 이하여도 모델 컨텍스트 예산을 넘으면 이유를 안내한다.

### 2.2 실행 상태

| 내부 상태 | 화면 표시 | 의미·가능한 다음 행동 |
| --- | --- | --- |
| queued | 대기 중 | 작업자가 실행을 시작하기 전 |
| running | 생성 중 | 실제 현재 단계 조회 |
| awaiting_input | 요구사항 확인 | 질문 답변 또는 미해결로 진행; 문서 교체 시 superseded 가능 |
| completed | 생성 완료 | 필수 검증 통과, 미해결 검토 항목 없음 |
| completed_with_warnings | 검토 필요 | 기술 오류는 없지만 질문·검토 후보 또는 DDL 미검증 존재 |
| completed_with_errors | 검증 실패 | 구조·DDL 검증 오류가 남음; 보완 후 새 실행 |
| failed | 실행 실패 | 파싱·모델·저장·시간 제한 등으로 처리 중단; 새 실행 가능 |
| superseded | 입력 교체로 종료 | 대기 중 입력 교체로 종료된 실행; 조회만 가능 |

질문 유무와 관계없이 요구사항 분석과 독립 리뷰가 끝나면 awaiting_input에서 사용자가 설계 진행을 결정한다. running에서 임의 취소는 MVP에 포함하지 않는다. 작업자 종료는 실패로 복구하고 자동 재개하지 않는다.

## 3. AG-00 프로젝트와 실행 시작

**연결 요구사항:** FR-001, FR-020.

- 입력: 프로젝트 이름·설명, 준비된 문서 리비전 ID, 실행 요청 멱등 키.
- 출력: 프로젝트 ID, 실행 ID, 상태와 조회 경로.
- 흐름: 프로젝트 생성 → 문서 선택 → 분석 시작 → 서버가 활성 실행 여부 확인 → 입력 스냅샷 저장 → queued 반환.
- 규칙: 프로젝트명 중복은 허용한다. 같은 멱등 키와 같은 요청은 기존 실행을 반환하며, 같은 키의 다른 요청은 거부한다. 활성 실행이 있으면 중복 생성을 차단한다.
- 예외: 문서가 다른 프로젝트 소속이거나 추출 준비가 안 됐으면 시작하지 않는다.
- 수용 시나리오: 시작 버튼을 두 번 눌러도 같은 실행 요청에서 작업이 하나만 생성된다. 앱 새로고침 후에도 프로젝트와 실행을 조회한다.

## 4. AG-01 문서 등록과 텍스트 추출

**연결 요구사항:** FR-002, FR-003.

- 입력: 프로젝트 ID와 지원 파일.
- 출력: 문서 리비전 ID, 추출 상태, 정규화 텍스트, 근거 위치 블록, 원문 해시.
- 흐름: 크기·형식 검증 → 내부 저장명 부여 → 비공개 저장 → 추출 → 블록별 위치 부여 → 제한 검사 → 미리보기 제공.
- 규칙: 확장자와 실제 내용 형식을 함께 검사한다. PDF는 페이지, DOCX는 문단·표 셀, TXT는 행 범위를 표시한다. DOCX에서 렌더링 페이지 번호를 추정하지 않는다. 변경 파일은 새 리비전으로 저장한다.
- 예외: 암호화 PDF, 스캔 문서, 손상 파일, 잘못된 TXT 인코딩, 빈 텍스트, 크기 초과는 구체적인 오류를 반환한다. 일부 내용만 추출 가능한 경우 누락 경고와 사용자 확인 없이 분석하지 않는다.
- 수용 시나리오: 같은 문장을 요구사항 근거에서 선택하면 업로드한 해당 리비전의 정확한 위치가 표시된다. 스캔 PDF는 정상 추출로 표시되지 않는다.

## 5. AG-02 요구사항 분석

**연결 요구사항:** FR-004, FR-005.

- 입력: 추출 텍스트와 블록 위치, 분석 설정.
- 출력: 요구사항 목록, 확인 질문 초안, 별도 요구사항 리뷰의 누락·중복·상충 후보.
- 필드: `id`, `text`, `kind`, `provenance`, `evidence`, `needs_confirmation`, `priority`, `priority_reason`.
- 흐름: 요구사항 단위 분리 → 기능·비기능 분류 → 근거 연결 → 스키마·인용 검사 → 별도 요구사항 리뷰 → 결과와 검토 후보 저장 → 사용자 확인 대기.
- 규칙: 리뷰는 원문과 분석 결과를 독립적으로 대조하고 누락·중복·상충·근거 부족 후보를 기록한다. 수정 지적이 있으면 조정 역할이 범위를 정해 분석을 최대 한 번 다시 실행하고 재리뷰한다. 원문 우선순위가 없으면 제안 또는 미정으로 표시한다. 상충하는 문장을 임의 병합·삭제하지 않으며 출처 없는 추가 요구는 proposal로만 기록한다. 리뷰 후보는 검증 통과나 사용자 결정으로 위장하지 않는다.
- 예외: 분석 또는 리뷰의 스키마 오류·근거 불일치는 제한된 재시도 후 실패시킨다. 모델이 빈 요구 목록을 반환하거나 리뷰가 끝나지 않으면 생성 완료로 표시하지 않는다.
- 수용 시나리오: “승인 이력을 보관한다”에 고유 ID와 원문 참조가 연결된다. 리뷰가 누락 후보를 지적하면 관련 원문 위치와 함께 사용자에게 표시하고, 원문에 없는 인용문은 검증에 실패한다.

## 6. AG-03 확인 질문과 답변

**연결 요구사항:** FR-006, FR-007.

- 입력: 질문 ID, 답변 또는 미해결 선택, 답변 버전.
- 출력: 답변 이력과 설계용 답변 스냅샷.
- 흐름: awaiting_input에서 질문·관련 원문 확인 → 답변 저장 → 설계 진행 선택 → 미해결 항목 확인 → 답변 동결 → queued로 전환.
- 규칙: 답변은 원문을 수정하지 않고 보완 근거로 저장한다. 답변이 새 모순을 만들면 검토 항목으로 남긴다. 빈 답변은 미해결이며 원문에 없던 정책을 자동 확정하지 않는다.
- 예외: running 이후 답변 수정 요청은 거부한다. 최신 답변 버전이 다르면 갱신 충돌을 안내한다. 문서 교체는 현재 대기 실행을 superseded로 마감하고 새 실행을 시작한다.
- 수용 시나리오: 긴급 승인 질문을 건너뛰어도 초안 생성은 가능하지만 최종 결과와 다운로드 문서에 미해결 사항이 표시된다.

## 7. AG-04 기능 명세 생성

**연결 요구사항:** FR-008.

- 입력: 요구사항, 답변 스냅샷, 미해결 질문.
- 출력: 고객 기능 ID별 이름·설명·행위자·입력·출력·선행 조건·처리 규칙·예외·우선순위·요구사항 연결.
- 흐름: 업무 행동 도출 → 기능별 명세 → 요구사항 연결 → 스키마·참조 검사.
- 규칙: 1개 요구사항이 여러 기능에 연결되거나 여러 요구사항이 한 기능에 연결될 수 있다. 정보가 없으면 빈 필드를 숨기지 않고 미정 사유를 남긴다. 보안·성능 요구사항은 별도 검증 항목으로 유지한다.
- 예외: 참조 요구사항이 없으면 구조 오류로 처리한다. 설계를 위한 추가 기능은 제안임을 표시한다.
- 수용 시나리오: 순차 승인·반려·재신청 요구에서 각 동작과 조건이 표현되며, 정의되지 않은 재승인 시작 단계는 확인 필요로 남는다.

## 8. AG-05 데이터 모델 생성

**연결 요구사항:** FR-009.

- 입력: 요구사항과 기능 명세, 답변, 미해결 사항.
- 출력: 테이블·컬럼·PK·UNIQUE·FK·관계·기본 제약을 가진 공통 모델 및 설계 근거.
- 흐름: 전체 요구사항·기능에서 테이블 카탈로그 작성 → 카탈로그 항목별 속성·키 병렬 설계 → 관계·기능 연결 → 전체 범위 누락 검사(cover) → 필요한 항목만 부분 수정(fix) → 구조 검사.
- 부분 수정의 입력은 현재 카탈로그·속성 결과와 누락·참조 오류로 한정한다. 수정하지 않은 테이블의 ID와 결과를 유지하고, 병렬 결과를 합칠 때 테이블·컬럼 ID의 고유성과 참조를 다시 검사한다.
- 규칙: PK, NULL 허용, 자료형과 길이를 명시한다. 관계의 다중성과 선택성이 FK·NULL·UNIQUE 구조로 표현되는지 검사한다. 임의 SQL 표현식은 모델 출력으로 허용하지 않는다. 코드로 구현해야 하는 규칙은 구현 책임을 application으로 표시하고 DDL 보장이라고 주장하지 않는다.
- 예외: 카탈로그나 병렬 속성 결과의 일부가 실패하면 완성 모델로 표시하지 않는다. cover/fix 이후에도 없는 컬럼 참조, 중복 식별자, FK 타입 불일치, 유일하지 않은 FK 대상이 남으면 오류다. 표현 불가능한 복잡한 제약은 미구현 검토 항목으로 남긴다.
- 수용 시나리오: 승인 이력을 보존하는 모델은 여러 승인 기록을 연결할 수 있어야 한다. 단순 이름 일치가 아닌 업무 규칙 충족 여부로 평가한다.

## 9. AG-06 ERD와 DDL 생성 및 검증

**연결 요구사항:** FR-010, FR-011.

- 입력: 구조 검증 완료 모델과 모델 해시.
- 출력: Mermaid ERD 원본·화면, PostgreSQL DDL, 검증 보고서.
- 흐름: 식별자·자료형 허용 목록 확인 → 동일 모델에서 ERD·DDL 렌더링 → 구조 비교 → 격리 DB 실행 → 결과 기록.
- 규칙: SQL은 모델이 자유 텍스트로 만든 문자열이 아니라 서버 생성기가 만든다. 테이블 생성 후 FK를 부여하여 순환 관계를 처리한다. SQL 검증은 테스트 전용 역할·환경에만 실행한다.
- 예외: 구조 오류는 렌더링과 배포용 다운로드를 차단한다. SQL 실행 실패는 SQL 다운로드를 차단한다. 검증 환경 미가용은 not_run으로 기록하고 경고를 표시한 SQL 초안만 제공한다.
- 수용 시나리오: FK를 일부러 잘못 연결하면 정상 DDL로 배포되지 않는다. 정상 모델은 테스트 DB 생성 후 실제 테이블·키 구조와 비교할 수 있다.

## 10. AG-07 추적표

**연결 요구사항:** FR-012, FR-013.

- 입력: 요구사항, 기능, 모델의 연결 정보.
- 출력: 요구사항별 기능·테이블·컬럼 ID, 연결 이유, 추적 상태, 비기능 검증 방법.
- 상태: linked, unlinked, not_applicable. not_applicable에는 이유를 필수 기록한다.
- 규칙: linked는 구조적으로 유효한 연결이 있음을 뜻하며 의미 정확성 통과를 뜻하지 않는다. 기능 요구사항 중 연결 대상인 항목을 분모로 연결률을 표시한다. 비기능 항목은 별도 표 또는 구분 열로 유지한다.
- 예외: 참조가 깨진 연결은 정상 링크로 표시하지 않고 검토 오류를 생성한다.
- 수용 시나리오: 승인 이력 보관 요구에 테이블 연결이 없으면 미연결로 표시한다. 응답 시간 요구에 테이블이 없다는 이유만으로 설계 오류를 만들지 않는다.

## 11. AG-08 누락과 모순 검토

**연결 요구사항:** FR-014, FR-015.

- 입력: 원문, 답변, 모든 설계 결과와 구조·추적 검사 결과. DDL 실행 검증은 이 단계 이후에 반영한다.
- 출력: 문제 ID, 유형, 심각도, 관련 ID, 근거, 설명, 수정 제안, 검토 처분.
- 유형: 구조 오류, 설계 누락 후보, 상충 후보, 정보 부족, 미구현 규칙, 검증 미실행.
- 흐름: 추적 연결·구조·누락의 결정적 규칙 검사 → 관련 ID·근거 유효성 확인 → 요구사항 리뷰 후보와 결과 병합 → 실행 완료 상태 결정.
- 규칙: 최종 검토자는 판단 가능한 규칙만 적용하고 구조 검증 통과를 업무 의미의 정확성으로 단정하지 않는다. 확인·오탐·보류 처분과 사유를 저장할 수 있다. 자동 복구는 출력 형식·참조 등 제한된 범위에서만 허용하며 변경 이유를 기록한다. 업무 정책의 의미 변경은 새 사용자 입력을 통한 새 실행으로 처리한다.
- 예외: 결정적 검토를 끝내 수행하지 못하면 검토 완료로 표시하지 않고 실행을 failed로 마감한다. 이미 생성한 결과는 진단용으로 보존한다.
- 수용 시나리오: 연결 대상인 요구사항이 기능·모델에서 누락되면 추적 관계의 누락 후보를 지적한다. 규칙으로 판정할 수 없는 업무 의미를 정상으로 확정하지 않으며, 오탐 처분으로 DDL 실패가 성공으로 바뀌지 않는다.

## 12. AG-09 결과 저장과 다운로드

**연결 요구사항:** FR-016~020.

- 입력: 프로젝트·실행 ID, 산출물 종류 또는 새 실행 요청.
- 출력: 실행 상세, 단계 상태, 오류, 허용 산출물 파일.
- 규칙: 완료 결과 JSON과 문서·답변·버전 스냅샷은 불변이다. 재생성은 부모 실행을 참조하되 고객 산출물 ID의 의미가 같다고 가정하지 않는다. 실제 모델 호출 실패를 샘플 결과로 대체하지 않는다.
- 다운로드: 요구사항·기능 명세·테이블 정의·검토 보고서 Markdown, 추적표 CSV, ERD Mermaid 원본, DDL SQL, 전체 결과 JSON. 파일 안에 실행 ID·검증 상태·미해결 사항을 포함한다.

| 조건 | 제공 정책 |
| --- | --- |
| 완료·검토 경고만 존재 | 모든 생성 산출물 제공, 경고 포함 |
| 구조 오류 존재 | 진단 JSON·검토 보고서·표시 가능한 텍스트 초안만 제공; ERD·SQL 차단 |
| 구조 정상·DDL 실행 실패 | ERD와 기타 초안 제공, SQL 배포용 다운로드 차단 |
| 구조 정상·DDL 미실행 | SQL은 미검증 초안 표시 후 제공 |
| 실행 실패 | 이미 저장한 진단 결과만 제공; 정식 완료 산출물로 노출하지 않음 |

수용 시나리오: 새로고침 후 완료 실행을 조회하고 동일 파일을 다운로드한다. 답변을 바꾸어 재생성하면 이전 실행은 그대로 유지된다.

## 13. 공통 오류 계약과 통합 수용

| 오류 코드 | 사용자 안내·복구 |
| --- | --- |
| INVALID_FILE / LIMIT_EXCEEDED | 지원 형식·제한을 안내하고 파일 변경 |
| EXTRACTION_FAILED / EMPTY_TEXT | 추출 가능한 문서 또는 TXT로 재등록 |
| ACTIVE_RUN_EXISTS / VERSION_CONFLICT | 현재 실행·최신 답변 조회 |
| INPUT_BUDGET_EXCEEDED | 내용 축소 또는 설정 재검토; 자동 누락 없음 |
| MODEL_UNAVAILABLE / STAGE_TIMEOUT | 원인과 실패 단계 표시, 새 실행 가능 |
| OUTPUT_INVALID / REFERENCE_INVALID | 제한 재시도 후 진단 결과와 실패 표시 |
| DDL_FAILED / DDL_NOT_RUN | 실행 실패와 환경 미가용 구분 |
| WORKER_INTERRUPTED / STORAGE_FAILED | 실패 기록 및 복구 후 새 실행 |

통합 검증에서는 정상 문서로 전체 다운로드까지 진행하고, 경계 크기·빈 문서·질문 미응답·중복 시작·잘못된 FK·모델 실패·작업자 재시작을 각각 주입한다. AI 품질은 동작 테스트와 분리하여 기준 답안으로 평가한다.

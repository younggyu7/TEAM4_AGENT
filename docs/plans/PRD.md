## 2. 제품 정의와 문제

기업의 서비스 요청·장애 관리 요구사항 문서를 받아 기능 명세와 데이터 설계 초안을 만들고, 각 설계의 근거 및 누락·모순 후보를 보여주는 웹 도구를 개발한다. 사람이 단계마다 확인·수정·확정하며, 최종본에는 개발 AI가 읽고 개발할 개발 스펙 문서를 함께 만든다.

요구사항 분석가는 자연어를 기능과 데이터 구조로 바꾸면서 같은 내용을 여러 문서에 옮긴다. 설계자는 승인·처리 이력과 같은 규칙이 데이터 모델에도 반영되었는지 다시 확인해야 한다. 문서에 없는 정책을 임의로 채우거나 연결 누락을 놓치면 개발 단계에서 재작업이 발생할 수 있다.

제품은 사용자가 검토할 수 있는 설계 초안과 근거를 함께 제공한다. 책임 범위는 요구사항의 출처 표시, 기능·데이터 설계 생성, 구조 검증, 사람이 판단할 검토 후보 제공, 확정한 설계의 개발 스펙(API·작업 목록·수용 기준) 생성이다. (검토 중) 팀장이 승인한 최종본으로는 서비스 코드(화면·API·DB)를 생성해 미리보기로 실행하고 git 저장소에 올릴 수 있다. 생성 코드는 개발을 이어 갈 출발점이며 운영 완성품이 아니다: 화면·등록·조회·수정·삭제·상태 바꾸기는 코드가 스펙대로 만들고, 업무 로직 빈칸만 선택적으로 AI가 채우며, 실제 인증·외부 연동·복잡한 업무 로직 검수는 사람이 한다. 이 제품(설계 도구)과 이 제품이 생성하는 앱은 구분한다.

## 3. 사용자와 핵심 과업

| 사용자 | 주요 과업 | 현재 어려움 | 제품이 제공할 가치 |
| --- | --- | --- | --- |
| 업무 분석가 | 고객 문서를 요구사항으로 정리 | 누락·불명확한 규칙 식별 | 원문 근거를 가진 요구사항 목록과 확인 질문 |
| 시스템 설계자 | 기능과 데이터 구조 구체화 | 기능·테이블의 일관성 검토 | 연결된 기능 명세·ERD·추적표 |
| 개발자 (개발 파트) | 설계 검토 및 구현 준비 | 키·타입·관계 오류, 규칙 누락 | 구조 검증 결과, 실행 가능한 DDL, API·작업 순서·수용 기준이 담긴 개발 스펙, 승인 최종본으로 생성한 서비스 코드·실행 미리보기 |

MVP는 교육용 가상 문서를 쓰는 한 팀(사내) 환경을 기본으로 한다. 화면은 회원가입·로그인(서버 세션)과 역할 권한을 둔다: 기획 파트가 기능 명세를 고치고 파트장이 확정, 데이터 파트가 ERD를 고치고 파트장이 확정, 팀장이 최종본을 승인하거나 수정을 지시하고, 개발 파트장이 승인한 최종본으로 최종 개발한다(권한표는 [요구사항 정의서](요구사항_정의서.md) FR-032~035·FR-038, 검토 중). 회원 승인·역할 지정은 관리자가 한다. 외부에 공개하는 다중 조직 서비스(조직별 분리, 프로젝트 소유권)는 별도로 설계한 후 추진한다.

## 4. 제품 원칙

- **근거를 확인할 수 있어야 한다.** 요구사항은 원문 구간 또는 사용자 보완 답변을 통해 출처를 확인한다.
- **모르는 정책을 확정하지 않는다.** 명시된 사실, 설계 제안, 확인 필요 항목을 구분한다.
- **연결 여부와 정확성을 구분한다.** 추적표에 링크가 있어도 내용이 맞다는 보장은 하지 않는다.
- **검증 결과를 숨기지 않는다.** 생성 완료와 구조·DDL 검증 상태를 별도로 표시한다.
- **이전 결과를 보존한다.** 다시 만들면 새 버전으로 저장하고 기존 버전을 덮어쓰지 않는다.
- **사람이 단계를 넘긴다.** 각 단계는 다음 단계를 스스로 시작하지 않고, 사람이 확인한 결과로만 다음 단계를 만든다. 사람이 확인한 것은 LLM 없이 반영해 비용을 줄인다.

## 5. 대상 업무와 MVP

서비스 요청은 계정 발급·접근 권한 신청, 승인·반려·재신청, 처리 이력을 대상으로 한다. 장애 관리는 접수·담당자 배정·처리·해결 확인·종료·재개와 이력을 대상으로 한다. 승인 순서, 우선순위 계산, 상태 전이 정책은 고객 입력에 따라 달라지며 제품 내부에 보편적 정답으로 고정하지 않는다.

| 우선순위 | 제품 기능 | 관련 기능 ID |
| --- | --- | --- |
| Must | 프로젝트와 설계 버전 조회 (업로드로 생성) | AG-00, AG-09 |
| Must | PDF·DOCX·HWPX·TXT 입력, 텍스트 추출 | AG-01 |
| Must | 요구사항 분류와 원문 근거 표시 | AG-02 |
| Must | 확인 질문 답변·'추천안 맞음' 확인, 미해결은 추천안으로 가정해 표시 | AG-03 |
| Must | 기능 명세, 데이터 모델, ERD·DDL 생성과 화면 직접 수정 | AG-04~06 |
| Must | 추적표와 누락·모순 후보 검토 (의미 검토는 ERD를 만들 때, 데이터 지적은 한 번 자동 보완) | AG-07~08 |
| Must | 결과 저장·다운로드, 실패 사유와 LLM 사용량 표시 | AG-09 |
| Should | 최종본의 API 설계와 개발 스펙 10개 | AG-10 |
| Should (검토 중) | 승인 최종본의 최종 개발하기(코드 생성), 예시 데이터·실행 미리보기(Docker), git 올리기 | AG-11 |
| Later | 분석 전 추출 미리보기 화면, 검토 처분(오탐·보류) 서버 저장 | 후속 범위 |
| Later | 다중 사용자 인증, 공동 편집, 외부 ITSM 연동 | 후속 범위 |

OCR, 이미지 중심 문서 분석, 변경·문제·구성 관리 전체, 다중 DB 방언, 운영 DB 자동 적용, 완성된 애플리케이션 코드 생성은 MVP에서 제외한다. 실행 간 차이 비교(`diff`)와 직접 수정은 0.5에서 Later였으나 지금 코드에 있다. RAG와 에이전트 수는 제품 성공 조건이 아니다.

## 7. 이용 흐름과 화면

1. 홈 '새 문서 분석'에서 문서를 올린다 (프로젝트 이름·사업 이름 선택). 프로젝트당 문서 한 건을 쓴다.
2. 문서 분석 → 요구사항 추출·검토 → 기능 명세 초안까지 만들고 멈춘다 (질문은 추천안으로 가정).
3. 기능 명세 화면에서 질문에 답하고, '(확인 필요)'·'(가정)' 규칙을 확인하고, 기능을 고친다.
4. 필수 항목을 다 해결하면 '내보내기 → ERD 만들기'(초록색)로 기능 명세를 확정하고 ERD·DDL 버전을 만든다. 이때 의미 검토가 빠진 데이터를 찾아 데이터 모델 Agent가 한 번 고친다.
5. ERD 화면에서 남은 의미 검토 지적마다 처리(반영함·문제 아님·미해결로 둠)를 고르고, 필요하면 테이블을 고쳐 새 ERD 버전을 만든다.
6. 'ERD 최종 확정하기'(초록색)로 최종본을 만든다 (DDL 검증·추적 검토·API 설계·개발 스펙). 확정은 취소하지 않고, 바꾸려면 새 버전을 만든다.
7. 최종 산출물 화면에서 결과·지적 처리·LLM 사용량을 보고 파일 또는 zip으로 받는다 (보기만 함).

| 화면 | 사용자 행동 | 필수 상태 표시 |
| --- | --- | --- |
| 홈 | 업로드, 프로젝트·버전 목록, 버전 제목 | 진행 중 작업, 버전별 LLM 사용량 |
| 기능 명세 | 질문 답변, 확인 필요 규칙·가정 확인, 기능 수정, 임시저장, 내보내기(확정), 확정 뒤 새 버전 만들기 | 원문 근거, 규칙 표시, 남은 필수 항목 |
| ERD | ERD 탐색, 테이블 수정·저장, 의미 검토 지적 처리, 최종 확정 | 구조 검사, 남은 지적, 작업 진행 상황 |
| 최종 산출물 | 결과 보기, 파일·zip 받기 | 지적과 처리, DDL 검증, LLM 사용량 |
| 산출물 보기 | 요구사항·질문·DDL·개발 스펙·추적·이슈·판단 기록 조회 | 완료 조건, 이슈 상태 |

생성 중에는 실행 기록과 경과 시간을 표시하며 근거 없는 완료 퍼센트를 제공하지 않는다. 확인할 항목과 미충족 완료 조건은 화면과 검토 보고서에 그대로 보여 준다.

## 8. 성공 지표와 출시 판단

가상 문서 8건을 초기 구성으로 삼는다. 기본·예외·정보 부족·상충 조건을 각각 두 건씩 준비하고, 조건별 한 건씩 개발용과 최종 평가용으로 분리한다. 정확한 분할과 채점 방법은 TRD의 평가 계획을 따른다.

| 지표 | 제안 목표 | 의미 |
| --- | --- | --- |
| 요구사항 추출 정밀도·재현율 | 각각 90% 이상 | 근거 없는 추가와 누락을 함께 평가 |
| 필수 기능 반영률·데이터 규칙 충족률 | 각각 90% 이상 | 핵심 업무를 설계로 표현 가능한지 평가 |
| 추적 연결 정확도·충족률 | 각각 90% 이상 | 잘못된 연결과 연결 누락을 함께 평가 |
| 문제 탐지 정밀도·재현율 | 각각 80% 이상 | 오탐과 미탐을 함께 평가 |
| DDL 실행 성공률 | 100% | 최종 평가의 모든 실행 기준 |
| ERD·DDL 구조 불일치 | 0건 | 동일 모델의 표현 간 일치 |

위 값은 달성 실적이 아니다. 지금은 문서 분석·요구사항 추출만 골든셋(문서 5개, `backend/evals`)으로 평가하고, 나머지 지표는 평가 도구가 없다. 실제 결과, 분자·분모, 실패 사례를 공개한다. 버전별 토큰 사용량은 검토 보고서에 기록한다.

MVP 시연 조건은 두 업무의 전체 흐름(업로드 → 기능 명세 확정 → ERD → 최종 확정), 정보 부족·상충 조건, 누락 검토, DDL 실행 검증, 결과 재조회·다운로드가 동작하는 것이다. 지표 미달 시 정상 완료로 숨기지 않고 결함과 개선 계획을 남긴다. 키 유출 방지, 실행 실패 표시가 동작하지 않으면 배포를 보류한다. 구조 오류가 있는 결과의 다운로드 차단은 지금 코드에 없다(오류를 검토 보고서에 표시).

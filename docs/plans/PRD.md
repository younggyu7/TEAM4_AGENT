본 문서는 제품이 해결할 문제, 사용자 경험, MVP 범위와 성공 기준을 정의한다. 구현 완료를 보고하는 문서가 아니다. 기술 구성과 성능 수치는 제안 기준이며 팀 검토 후 확정한다.

## 2. 제품 정의와 문제

기업의 서비스 요청·장애 관리 요구사항 문서를 받아 기능 명세와 데이터 설계 초안을 만들고, 각 설계의 근거 및 누락·모순 후보를 보여주는 웹 도구를 개발한다.

요구사항 분석가는 자연어를 기능과 데이터 구조로 바꾸면서 같은 내용을 여러 문서에 옮긴다. 설계자는 승인·처리 이력과 같은 규칙이 데이터 모델에도 반영되었는지 다시 확인해야 한다. 문서에 없는 정책을 임의로 채우거나 연결 누락을 놓치면 개발 단계에서 재작업이 발생할 수 있다.

제품은 사용자가 검토할 수 있는 설계 초안과 근거를 함께 제공한다. 책임 범위는 요구사항의 출처 표시, 기능·데이터 설계 생성, 구조 검증과 사람이 판단할 검토 후보 제공이다.

## 3. 사용자와 핵심 과업

| 사용자 | 주요 과업 | 현재 어려움 | 제품이 제공할 가치 |
| --- | --- | --- | --- |
| 업무 분석가 | 고객 문서를 요구사항으로 정리 | 누락·불명확한 규칙 식별 | 원문 근거를 가진 요구사항 목록과 확인 질문 |
| 시스템 설계자 | 기능과 데이터 구조 구체화 | 기능·테이블의 일관성 검토 | 연결된 기능 명세·ERD·추적표 |
| 개발자 | 설계 검토 및 구현 준비 | 키·타입·관계 오류, 규칙 누락 | 구조 검증 결과와 실행 가능한 DDL 초안 |

MVP는 교육용 가상 문서를 사용하는 로컬 단일 운영자 환경을 기본으로 한다. 사용자 유형은 이용 목적의 구분이며, 역할별 로그인·권한 체계를 뜻하지 않는다. 외부에 공개하는 다중 사용자 서비스는 인증과 소유권 검증을 별도로 설계한 후 추진한다.

## 4. 제품 원칙

- **근거를 확인할 수 있어야 한다.** 요구사항은 원문 구간 또는 사용자 보완 답변을 통해 출처를 확인한다.
- **모르는 정책을 확정하지 않는다.** 명시된 사실, 설계 제안, 확인 필요 항목을 구분한다.
- **연결 여부와 정확성을 구분한다.** 추적표에 링크가 있어도 내용이 맞다는 보장은 하지 않는다.
- **검증 결과를 숨기지 않는다.** 생성 완료와 구조·DDL 검증 상태를 별도로 표시한다.
- **이전 결과를 보존한다.** 재생성은 새 실행으로 저장하고 기존 결과를 덮어쓰지 않는다.

## 5. 대상 업무와 MVP

서비스 요청은 계정 발급·접근 권한 신청, 승인·반려·재신청, 처리 이력을 대상으로 한다. 장애 관리는 접수·담당자 배정·처리·해결 확인·종료·재개와 이력을 대상으로 한다. 승인 순서, 우선순위 계산, 상태 전이 정책은 고객 입력에 따라 달라지며 제품 내부에 보편적 정답으로 고정하지 않는다.

| 우선순위 | 제품 기능 | 관련 기능 ID |
| --- | --- | --- |
| Must | 프로젝트 생성과 실행 이력 조회 | AG-00, AG-09 |
| Must | PDF·DOCX·TXT 입력, 텍스트 추출·미리보기 | AG-01 |
| Must | 요구사항 분류와 원문 근거 표시 | AG-02 |
| Must | 불명확 항목의 답변 입력 및 미해결 상태 유지 | AG-03 |
| Must | 기능 명세, 데이터 모델, ERD·DDL 생성 | AG-04~06 |
| Must | 추적표와 누락·모순 후보 검토 | AG-07~08 |
| Must | 결과 저장·다운로드와 실패 사유 표시 | AG-09 |
| Later | 선택 구간 재생성, 실행 간 차이 비교, 직접 모델 편집 | 후속 범위 |
| Later | 다중 사용자 인증, 공동 편집, 외부 ITSM 연동 | 후속 범위 |

OCR, 이미지 중심 문서 분석, 변경·문제·구성 관리 전체, 다중 DB 방언, 운영 DB 자동 적용, 완성된 애플리케이션 코드 생성은 MVP에서 제외한다. RAG와 에이전트 수는 제품 성공 조건이 아니다.

## 6. 핵심 사용자 스토리

| ID | 사용자 스토리 | 수용 기준 |
| --- | --- | --- |
| US-01 | 분석가로서 추출된 문서를 확인하여 잘못 읽힌 입력으로 설계하는 일을 피하고 싶다. | 분석 전 추출 본문과 위치를 조회하며 추출 실패를 구분한다. |
| US-02 | 분석가로서 불명확한 승인 정책을 보완하고 싶다. | 질문에 답하거나 미해결로 남길 수 있고, 다음 실행에 그 상태가 반영된다. |
| US-03 | 설계자로서 요구사항에 연결된 기능·ERD를 확인하고 싶다. | 항목을 선택하면 관련 ID와 근거를 확인한다. |
| US-04 | 설계자로서 승인 이력 같은 규칙이 빠졌는지 알고 싶다. | 문제 후보에 원문·관련 설계·수정 제안이 표시된다. |
| US-05 | 개발자로서 SQL의 구조적 유효성을 확인하고 싶다. | 생성 SQL과 테스트 DB 검증 결과를 별도로 확인한다. |
| US-06 | 사용자로서 입력을 보완한 뒤 이전 결과와 구별하고 싶다. | 새 실행 ID와 상위 실행 ID가 저장되고 과거 결과를 다시 조회한다. |

## 7. 이용 흐름과 화면

1. 프로젝트 이름과 설명을 등록한다.
2. 문서를 업로드하고 추출 결과를 확인한다. 초기에는 실행당 문서 한 건을 사용한다.
3. 분석을 시작하여 요구사항과 확인 질문을 받는다.
4. 답변을 작성하거나 미해결 상태로 설계 진행을 선택한다.
5. 기능·데이터 설계, 산출물 변환, 검증·검토가 순차 실행된다.
6. 결과와 검토 사항을 확인한다. 구조 오류가 남은 경우 ERD·SQL 배포용 다운로드는 차단한다.
7. 입력을 보완해 새 실행을 만들거나 허용된 산출물을 다운로드한다.

| 화면 | 사용자 행동 | 필수 상태 표시 |
| --- | --- | --- |
| 프로젝트·문서 | 생성, 업로드, 추출 미리보기, 실행 선택 | 추출 성공·실패, 현재 실행 |
| 요구사항 확인 | 근거 조회, 질문 답변, 설계 진행 | 원문 근거·제안·확인 필요 |
| 기능 명세 | 기능별 조건·규칙·예외 조회 | 연결 요구사항, 잠정 항목 |
| 데이터 설계 | ERD 탐색, 테이블·SQL 조회 | 구조 검증, DDL 검증 상태 |
| 추적·검토 | 연결과 문제 조회, 검토 처분 기록 | 심각도, 근거, 미해결 사유 |
| 실행 결과 | 과거 결과 조회, 다운로드 | 실행 버전·생성 모드·실패 단계 |

생성 중에는 실제 현재 단계와 경과 시간을 표시하며 근거 없는 완료 퍼센트를 제공하지 않는다. 확인 필요 사항이 남은 완료는 ‘검토 필요’, 기술 오류가 있는 결과는 ‘검증 실패’로 표시한다.

## 8. 성공 지표와 출시 판단

가상 문서 8건을 초기 구성으로 삼는다. 기본·예외·정보 부족·상충 조건을 각각 두 건씩 준비하고, 조건별 한 건씩 개발용과 최종 평가용으로 분리한다. 정확한 분할과 채점 방법은 TRD의 평가 계획을 따른다.

| 지표 | 제안 목표 | 의미 |
| --- | --- | --- |
| 요구사항 추출 정밀도·재현율 | 각각 90% 이상 | 근거 없는 추가와 누락을 함께 평가 |
| 필수 기능 반영률·데이터 규칙 충족률 | 각각 90% 이상 | 핵심 업무를 설계로 표현 가능한지 평가 |
| 추적 연결 정확도·충족률 | 각각 90% 이상 | 잘못된 연결과 연결 누락을 함께 평가 |
| 문제 탐지 정밀도·재현율 | 각각 80% 이상 | 오탐과 미탐을 함께 평가 |
| DDL 실행 성공률 | 100% | 최종 평가의 모든 실행 기준 |
| ERD·DDL 구조 불일치 | 0건 | 동일 모델의 표현 간 일치 |

위 값은 달성 실적이 아니다. 실제 결과, 분자·분모, 실패 사례를 공개한다. 문서별 실행 시간·토큰 사용량·재시도 횟수도 기록하되 아직 속도 개선 효과를 주장하지 않는다.

MVP 시연 조건은 두 업무의 전체 흐름, 정보 부족·상충 조건, 누락 검토, DDL 실행 검증, 결과 재조회·다운로드가 동작하는 것이다. 지표 미달 시 정상 완료로 숨기지 않고 결함과 개선 계획을 남긴다. 구조 오류가 있는 결과의 다운로드 차단, 키 유출 방지, 실행 실패 표시가 동작하지 않으면 배포를 보류한다.

## 9. 미결정 사항

구현 현황과 실행 방법은 [프로젝트 README](../../README.md)와 [TRD](TRD.md)에서 확인한다.

| 결정 사항 | 담당 역할 | 현재 기준 |
| --- | --- | --- |
| 실제 인원·일정 | 팀 전체 | 작업 착수 시 배정 |
| 모델·예산 상한 | AI·기획 | 샘플 비교 후 확정 |
| 입력 크기·시간 제한 | 백엔드·AI | 기능 명세서의 초기 제한 사용 |
| UI 기술 | 프론트엔드 | React 기반 UI 제안, TRD 참조 |
| 외부 공개 여부 | 팀 전체 | 로컬 단일 운영자 기준 |

범위나 기준 변경 시 본 문서와 요구사항 정의서의 수용 기준을 먼저 수정하고 기능 명세·TRD 및 평가 기준에 반영한다.
